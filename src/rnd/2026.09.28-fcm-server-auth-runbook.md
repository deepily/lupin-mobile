## The short answer

**You don't need a new key.** The Google credentials you already refresh every day (gcloud "Application Default Credentials") can send FCM pushes for the app's Firebase project. I proved that today with a dry run (below). What's missing is only plumbing: the server container can't see those credentials yet, and it's configured for the other login method. It takes three small config changes and one container recreate.

## Route A (recommended): use your daily credentials, no new key

### Step 1: you, once a day, as now

Keep running `gcloud auth application-default login` when you normally do. Nothing new. (The quota project is already set to `hello-world-foo-423219`; to confirm, `gcloud auth application-default print-access-token` should print a token without error.)

### Step 2: let the container see the credentials (`lupin/docker-compose.yml`, service `lupin-rest-dev`)

Add one volume and one environment variable:

```yaml
    volumes:
      # FCM wake-ups (row 8ff78c69): Rick's daily gcloud ADC login, read-only.
      # Mount the DIRECTORY, not the single file: gcloud rewrites the file by
      # replacing it, and a single-file bind would keep pointing at the old copy.
      - ${HOME}/.config/gcloud:/home/rruiz/.config/gcloud:ro
    environment:
      # firebase_admin can't infer the project from user credentials.
      - GOOGLE_CLOUD_PROJECT=hello-world-foo-423219
```

### Step 3: switch the server's FCM login method (`lupin/src/conf/lupin-app.ini`)

```ini
fcm wake auth mode                      = adc
```

(It currently says `key_file`. The `adc` path is already built and tested: `fcm_wake_service.py`, `_init_real_transport_adc`.)

### Step 4: recreate the dev server

A plain restart **isn't enough**: mounts and environment are fixed when the container is *created*. The fleet's bounce script handles this. It warns every session, waits for acknowledgements, notices that `docker-compose.yml` changed ("compose drift"), and recreates rather than restarts. From `lupin/`:

```bash
src/scripts/bounce-dev-server.sh    # detects the compose change and runs docker compose up -d --force-recreate
```

### Step 5: check that it's on

In the boot log (`docker logs lupin-rest-dev 2>&1 | grep FCM-WAKE`), expect:

```
[FCM-WAKE] Enabled — Firebase app 'lupin-fcm-wake' initialized (ADC)
```

If it still says `DISABLED`, the line names the exact reason (library missing, credentials not found, or init error).

### The one caveat with Route A

The server reads your credentials **once, at boot**, then keeps renewing short-lived access tokens with the refresh token from that file. If the reason you log in daily is that your login **expires** daily (a Google session-length policy), the server's copy expires too. Wake-ups would then fail with a refresh error until the server is restarted. It wouldn't be silent: the send failure is logged, and `8ff78c69` will catch it in slice 7.

Two ways to handle it if it bites:
- **Simple:** bounce `:7999` after your daily login.
- **Better (a small server change, a follow-up ticket):** on a refresh failure, `fcm_wake_service.py` re-reads the credentials file and retries once. Because the directory is mounted, it would pick up your fresh login automatically.

If your daily login is a habit rather than an expiry, none of this applies. The refresh token keeps working until it's revoked.

## Route B (fallback): a Firebase service-account key

Use this only if Route A's expiry becomes a nuisance. A service-account key never expires with your login, but it's a long-lived secret file to protect.

1. Firebase console → project **hello-world-foo-423219** → ⚙ Project settings → **Service accounts** → **Generate new private key**. It downloads a JSON file.
   - If Google refuses with an organization-policy message (`iam.disableServiceAccountKeyCreation`), key downloads are blocked for your account; stay on Route A.
2. Put the file on the server outside every git repo, e.g. `~/.lupin/fcm-service-account.json`, with `chmod 600`. `~/.lupin` is already mounted into the container at the same path.
3. `docker-compose.yml`, `lupin-rest-dev` → `environment:` add `FCM_SERVICE_ACCOUNT_JSON=/home/rruiz/.lupin/fcm-service-account.json`.
4. Leave `fcm wake auth mode = key_file` (the current setting).
5. Recreate `:7999` (Route A, step 4), then check for `... initialized (key_file from FCM_SERVICE_ACCOUNT_JSON)`.
6. Confirm the project: the key's `"project_id"` must be `hello-world-foo-423219`.

## Appendix: the dry-run check, rerunnable any time

Run it on the server from any directory. It mounts your gcloud directory read-only into a throwaway container and sends **nothing** to any device:

```bash
cat > /tmp/fcm-dry-run.py <<'EOF'
import firebase_admin
from firebase_admin import credentials, messaging
app = firebase_admin.initialize_app( credentials.ApplicationDefault(), name="adc-dry-run" )
print( "app project:", app.project_id )
msg = messaging.Message( token="fake-token-for-dry-run", data={ "type": "ws_wake" },
                         android=messaging.AndroidConfig( priority="high" ) )
try:
    messaging.send( msg, dry_run=True, app=app ); print( "RESULT: accepted" )
except Exception as e:
    print( "RESULT:", type( e ).__name__, "|", str( e )[ :220 ] )
EOF
docker run --rm --user $(id -u):$(id -g) -e HOME=/home/rruiz \
  -e GOOGLE_CLOUD_PROJECT=hello-world-foo-423219 \
  -v $HOME/.config/gcloud:/home/rruiz/.config/gcloud:ro \
  -v /tmp/fcm-dry-run.py:/tmp/dry.py:ro \
  --entrypoint python lupin:1.1.3-testtoolchain-candidate /tmp/dry.py
```

**Good:** `RESULT: UnregisteredError | NotRegistered` (authenticated and allowed; only the fake token was refused).
**Bad:** anything mentioning `PERMISSION_DENIED`, `401`, `RefreshError` or `invalid_grant`. The login expired or lacks FCM rights; rerun `gcloud auth application-default login`.
