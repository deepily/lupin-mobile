2. Plug the phone into the laptop with the USB cable. If the phone asks "Allow USB debugging?", tap **Allow**.
3. On the laptop, check that the phone is visible:
   ```bash
   adb devices
   ```
   You should see exactly one line ending in `device`.
4. On the laptop, run the build-and-deploy script from the dev server share:
   ```bash
   cd /Volumes/data/include/www.deepily.ai/projects/lupin-mobile/src/scripts && ./build-and-deploy-lupin-mobile.sh
   ```
   (If you have the `bndm` alias, that's the same command.) It copies the code to `~/Projects/lupin-mobile`, builds a debug APK, installs it on the phone, and opens the app.
5. When you see **"APK installed"** and the log starts scrolling, press **Ctrl+C** to stop the log. The app stays installed.
6. **On the phone, select LAN DEV on the server switch, then log in.** The app starts on DEV, the emulator-only address, so signing in before switching fails with a connection error.
   1. The app opens on the **Sign in** screen. (If it shows a fingerprint **Unlock** screen instead, tap **Use password instead**.)
   2. Below the **Sign in** button is the server switch: an **Active server** line (`DEV · http://10.0.2.2:7999`) above a row of buttons **DEV | TEST | LAN DEV | LAN TEST**. Close the keyboard or scroll down if it's hidden.

   4. Check that the badge at the top right of the screen now reads **LAN DEV** and the Active server line reads `LAN DEV · http://192.168.1.21:7999`.
   5. Enter your email and password and tap **Sign in**.

   The choice is remembered, so later launches stay on LAN DEV. To go back to the emulator server, switch back to **DEV** the same way (the switch is on the Sign in screen, so log out first).

## Part 3: Check 2, Opus accuracy (row `9b1f7701`, about 7 minutes)

The question: if the phone sent compressed Opus audio at 32 kbps instead of WAV, would the transcripts get worse? To answer it we need real recordings of your voice, made by the app's own microphone path.

### Honest status: the app does not keep its recordings today

The app records to a WAV file (44.1 kHz, mono, 16-bit; `lib/services/asr/asr_service.dart:43-47`) in its private cache folder (`asr_service.dart:90-91`), and **deletes it as soon as the upload finishes**, whether the upload worked or not:

- Review-first Quick Ask and focus-mode voice replies delete it in `stopAndTranscribe()`'s cleanup (`asr_service.dart:191-193`), which calls `discardPendingUpload()`, which deletes the file (`asr_service.dart:146-148`).
- Send-immediately Quick Ask deletes it through the same `discardPendingUpload()`, called from `quick_ask_bloc.dart:416-419`.

So nothing is left on the phone to pull, and the cache folder isn't reachable with `adb pull` anyway.

**Smallest change that would fix it** (not built): in `AsrService.discardPendingUpload()`, when a debug switch is on, copy the WAV to the app's external files folder (`/sdcard/Android/data/ai.deepily.lupin_mobile/files/asr-recordings/`) before deleting it. Because both capture paths already go through that one method, that is one copy call plus the switch: either a "Keep voice recordings" toggle in Settings → Debug, or a build-time flag passed by the build script. Roughly 20 lines plus a test.

If the build doesn't have that change, **skip this check today**. Don't substitute the phone's own voice recorder app: it records differently and usually already compresses the audio, which is the very thing we're trying to measure.

### If the build keeps recordings: what you do

21. In the app, open the side menu, tap **Quick Ask**, and set the switch to **Review first**. Tap the mic button to start recording each question, and tap it again to stop. The transcript appears as a draft; tap the red **✕ (Clear)** button so nothing is sent as a job.
22. Record about 10 real questions. Before each one, write down (or type) **exactly** what you're going to say; that text is the answer key. Aim for a mix like this:

    | # | Length | What makes it hard | Example |
    |---|---|---|---|
    | 1 | ~3 s | very short | "What time is it?" |
    | 2 | ~5 s | a name and a time | "Remind me to call Dr. Nakamura at 4:45 tomorrow." |
    | 3 | ~6 s | numbers and units | "Convert 37.5 degrees Celsius to Fahrenheit." |
    | 4 | ~6 s | place name | "What's the weather in Albuquerque this weekend?" |
    | 5 | ~8 s | project jargon | "How many open pull requests are there on lupin-mobile?" |
    | 6 | ~10 s | technical words | "Did the Whisper pod on Kubernetes restart overnight, and how many times?" |
    | 7 | ~12 s | codec terms, numbers | "Explain the difference between Opus and AAC at 32 kilobits per second." |
    | 8 | ~15 s | long, several clauses | Your own: a question about the WebSocket reconnect logic and last week's commits |
    | 9 | 25 to 30 s | longest, rambling | Your own: a real multi-part question you'd actually ask |
    | 10 | ~6 s | **noisy room** | "Add oat milk, sourdough and two pounds of Honeycrisp apples to the grocery list." with a TV, kitchen or street noise behind you |

    Use your own questions if you prefer; what matters is the mix and the written answer key.
23. Pull the recordings and your answer key to the laptop. Recordings are in the app's **internal** storage (`files/recordings/`), because since Android 11 `adb pull` can't read the old `/sdcard/Android/data/…` folder (corrected 2026-09-16, row 4be8fe63). List them, then copy each one with `run-as`:
    ```bash
    mkdir -p ~/Desktop/asr-recordings && cd ~/Desktop/asr-recordings
    for f in $( adb exec-out run-as ai.deepily.lupin_mobile ls files/recordings ); do
        adb exec-out run-as ai.deepily.lupin_mobile cat "files/recordings/$f" > "$f"
    done
    ls -l      # each WAV should be tens or hundreds of KB; a ~100-byte file is an error message, not audio
    ```
24. Copy that folder and the answer key onto the dev server share and tell the seat where they are. You're done.

### What the seat does afterwards (no action from you)

1. **Make the Opus copies on the desktop.** For each WAV, encode to Opus at 32 kbps, then decode it back to a WAV at the original sample rate, so the compressed and uncompressed versions go through exactly the same transcription endpoint and only the codec differs:
   ```bash
   ffmpeg -i q01.wav -c:a libopus -b:a 32k -application voip q01.opus
   ffmpeg -i q01.opus -ar 44100 -ac 1 -c:a pcm_s16le q01-opus.wav
   ```
   (For the AAC half of the row, the same pattern with `-c:a aac -b:a 32k q01.m4a`.)
2. **Transcribe both versions on the test server.** Wait for `venue_idle` to exit 0, then submit the originals and the Opus round-trips through the `:8000` test-suite door (`POST /api/test-suite/submit`), never as ad hoc requests to `:8000`.
3. **Compare word by word.** Normalise case and punctuation, then for each clip compare the WAV transcript and the Opus transcript against your answer key: count substituted, missing and extra words, and list every word where the two versions differ. Pay special attention to names, numbers and technical words, and to the noisy-room clip.
4. **Report** a per-clip table (words wrong on WAV, words wrong on Opus, which words changed) and a one-line verdict for row `9b1f7701`.

**Caveat on the result**: the desktop's Opus encoder (libopus through ffmpeg) is not the encoder the phone would use (Android's built-in one, reached through the app's recording library). They differ in tuning and framing, so this check shows whether **Opus at 32 kbps as a format** hurts accuracy on your voice. It does not prove the phone's own encoder will behave identically; if the result is close, a follow-up recording made on the phone in Opus settles it.
