# Problem statement: after a push wake-up, how does a backgrounded Flutter Android app get its WebSocket back?

*For a deep-research run. Scope is deliberately narrow: everything up to "the phone received the wake-up" is already built.*

## Setup

- **App:** Lupin AF, a Flutter app (Dart), Android only. It is a voice-first client for a self-hosted FastAPI server. It uses `firebase_messaging` 15.x, `flutter_local_notifications`, `flutter_tts`, and a single app-wide WebSocket (`/ws/queue`) for live notifications and agent traffic.
- **Server:** on a home LAN, no public IP. It reaches Firebase Cloud Messaging outbound only.
- **Phone:** a Pixel-class phone on current Android (assume Android 14–15), on the same home Wi-Fi. Off-LAN use is out of scope until late October.
- **Builds:** debug APKs, installed over adb. Not distributed through the Play Store.

## What already works (or is built and waiting to be switched on)

1. When a notification is queued for a user who has **no live mobile WebSocket**, the server sends a **data-only, high-priority FCM message** carrying no content (`ws_wake`), at most one per user per 60 s.
2. The app registers its FCM token at login, when Google replaces the token, and on every WebSocket reconnect.
3. The background FCM handler runs in a **separate background isolate**, with no access to the main isolate's services. It exchanges a token for auth, fetches **one** notification over HTTP, shows it as a local notification, and speaks it if the user's settings allow. By design it **never touches the WebSocket**.

## The open question

The owner now wants the app to **go quiet in the background and, when woken by a push, get its live WebSocket connection back**, so that the full conversation traffic resumes, not just a single fetched notification.

Please research and recommend:

1. **What Android actually allows** after a high-priority FCM data message wakes a backgrounded or killed app: how long it may run, whether it may start a foreground service from that handler (Android 12+ restrictions and their FCM exemption; Android 14's required foreground-service types and their policy rules), and how Doze and App Standby buckets change this.
2. **Options for getting the socket back**, with pros, cons and battery cost for each:
   - (a) The wake-up only shows a notification; tapping it resumes the app, which reconnects. This is the current design plus a tap target.
   - (b) The wake-up starts a **short-lived foreground service** that opens the WebSocket, drains the waiting traffic, then stops.
   - (c) A **long-lived foreground service** keeps the WebSocket open whenever the user wants "live" mode, with a permanent notification.
   - (d) Anything better, e.g. Android's newer mechanisms for this kind of work, or letting the WebSocket die and relying on FCM plus HTTP fetches alone.
3. **The Flutter specifics:** which packages are maintained and suitable in 2026 (e.g. `flutter_foreground_task`, `flutter_background_service`, or native Kotlin through a platform channel); how a service-owned socket and the main isolate's UI share one connection, or hand it over, without two sockets fighting; and the reconnect and auth handshake from a background isolate.
4. **How to test it incrementally:** what can be proven on an emulator with a Google Play services image (including forcing Doze with `adb shell dumpsys deviceidle force-idle` and App Standby buckets), and what can only be proven on the physical phone.

## Constraints and preferences

- Smallest possible steps, each testable on its own; emulator first, phone second.
- Battery matters, but "live mode" with a visible notification is acceptable if it is the only reliable path.
- No new always-on cloud relay; the server stays on the LAN and FCM remains the only external channel.
- The server's wake-up contract (data-only, no content) should stay as it is unless there's a strong reason to change it.

## Wanted back

A recommendation (a/b/c/d) with rationale; the exact Android constraints that decide it, with sources; a step-by-step build and test sequence; and the failure modes to test for (token rotation, server restart, network change, Doze exit).
