# JDK 25 build failure — why upgrading Gradle does not fix it

Date: 2026-09-15 · Author: Tiffany 💍 (research subagent, read-only) · Rows: c51e92da, 9b1f7701

## Correction — 2026-09-15, later the same day

**This document said "Android Studio bundles JBR 21". That was wrong for the Studio Rick is
running, and it is the line that produced a recommendation that cannot work.**

The original row read *"Android Studio bundled JDK — JBR 21 (since Ladybug 2024.2.1)"*, with no
upper bound. Read literally it says: whatever Studio you have, its bundled Java is 21. So the
obvious next move — *"skip the download, just point the build at Android Studio's bundled JBR"* —
looked free. It is not free. **Android Studio 2026.1 (Quail) bundles JBR 25.0.3.** On that Studio

A second thing was wrong with it: the working theory had been that Flutter "failed to detect Android
Studio". It detected it fine. `flutter doctor -v` names the exact binary —

resolving Studio's JBR first is the documented order. There is no detection bug to chase.

**The fix is unchanged and is now the only fix: install a separate JDK 21 and point Flutter at it**

2026.1. The corrected, version-dependent row is in the table below.

## The question

The laptop build died with a bare `25.0.3` as its entire error. First recommendation was "install
JDK 21 and point Flutter at it". Rick pushed back, correctly: *why not upgrade Gradle to something
that supports JDK 25, rather than install an older Java?* This is the evidence.

## Answer: Gradle is not the blocker — Flutter's own tooling is

The vendored SDK caps what it will accept, in
`flutter/packages/flutter_tools/lib/src/android/gradle_utils.dart`:

```
maxKnownAndSupportedGradleVersion = '8.12'
maxKnownAndSupportedAgpVersion    = '8.7.3'
```

Those are **exactly** the versions this repo pins. We are already at Flutter 3.32's ceiling, so
there is no Gradle 9 to move to without moving Flutter first. Flutter 3.32's own Java table stops at
a `javaMax` of 24 — and that bound is exclusive, so the highest Java it knows about is 23.
(Flutter 3.35.1 is identical here; see the third question below.)

And the destination is not supported either: **AGP has never listed JDK 25**. AGP 9.4.0 (Sept 2026,
current) still says JDK 17 minimum and default. `flutter/flutter#187223`, "Java 25 Support in Flutter
Android Builds" (opened 2026-05-28), is still open and reports real breakage on JDK 25 — its own
suggested workaround is to use JDK 17 or 21.

## Is JDK 21 "old"?

No — it is the current LTS and what the Android toolchain targets. Flutter resolves Android Studio's
bundled Java first, then `JAVA_HOME`, then PATH — so on a Studio that bundles 21 you get 21 for
free, and on Studio 2026.1 that same rule hands you the 25.0.3 that breaks the build. JDK 25 is the
*newer* one, not the *supported* one; nobody builds Android on 25 today.

| Path | Files touched | Time | Risk |

## Second question: how far behind is our Flutter, and is upgrading worth anything?

Vendored: **3.32.0**, stable, framework commit 2025-05-19, Dart 3.8.0. Current stable: **3.47.2**
(the docs site's own stamp as of 2026-09-15), Dart 3.13.x — five stable releases (3.35, 3.38, 3.41, 3.44, 3.47) and about 15 months.

- **It is the only unlock for Gradle 9**, since `flutter_tools` refuses anything above its cap.
  3.44 introduced AGP 9 support; 3.47 ships AGP 9.1.0 / Gradle 9.3.1 / KGP 2.4.0 templates. But
  3.47's verified set still says Java 17 minimum, and AGP still does not list 25.
- **What it would break here**: the AGP 9 + built-in-Kotlin migration rewrites `android/`. `minSdk`
  is already 24, so that bug does not touch us. On the pub side most direct deps are a major behind
  and get dragged forward: `flutter_bloc` 8→9, `web_socket_channel` 2→3, `connectivity_plus` 5→6+,
  `flutter_local_notifications` 17→19+, `share_plus` 10→11, `get_it` 7→8, `freezed` 2→3,
  `flutter_lints` 3→6, plus `flutter_sound` 9.x which `pubspec.yaml` already flags as debt.
- **Does the app need anything in those releases? No.** No fix matching a bug we have, no
  audio/recording fix for our stack, no security advisory. Under the standing policy — upgrade only
  when something breaks or something needed requires it — there is no compelling reason.

## Third question: the laptop runs Flutter 3.35.1, not the vendored 3.32.0 — does that change anything?

It does not. But it is worth spelling out, because the whole argument above was computed from
3.32's caps and the laptop never loads 3.32.

### Which Flutter actually builds this app

**On the laptop: his own 3.35.1. The vendored 3.32.0 is not even present there.** Three reasons,
each independently sufficient:

| Mechanism | What it does | Where |
|---|---|---|
| The deploy script calls bare `flutter` | `flutter pub get` · `flutter build apk --debug` — no path, so it resolves on `PATH` → `~/flutter/v3.35.1` | `src/scripts/build-and-deploy-lupin-mobile.sh` |
| `flutter build` **rewrites** `flutter.sdk` | `updateLocalProperties()` sets `flutter.sdk` to the SDK root of whichever `flutter` binary ran | `gradle_utils.dart:751` (`Cache.flutterRoot`) |
| The laptop rsync **excludes** `flutter/` | the vendored SDK is never copied to `~/Projects/lupin-mobile` | `src/scripts/rsync-lupin-mobile.sh` |

So `android/local.properties` does **not** pin the SDK — it is a generated cache of the last SDK
that built, and Gradle only reads it back to locate `flutter_tools/gradle`
( `android/settings.gradle.kts` ). It is tracked in git, which is why it churns per machine.
`./flutter.sh` is the only way to get the vendored 3.32.0, and only on the dev server.

⇒ **His 3.35.1 is the relevant Flutter for any build he runs tonight.**

### What 3.35.1's caps actually are

Read from the 3.35.1 tag's own `gradle_utils.dart`, not from release notes:

| Constant | 3.32.0 (vendored) | 3.35.1 (his laptop) | Moved? |
|---|---|---|---|
| `maxKnownAndSupportedGradleVersion` | `8.12` | `8.12` | **no** |
| `maxKnownAndSupportedAgpVersion` | `8.7.3` | `8.9.1` | yes |
| `templateAndroidGradlePluginVersion` | `8.7.3` | `8.9.1` | yes |
| `oneMajorVersionHigherJavaVersion` | `24` | `24` | no |
| top `_javaGradleCompatList` row | `javaMin 23 · javaMax 24` (max exclusive) | identical | no |
| top `_javaAgpCompatList` row | `javaMin 17 · javaDefault 17` | identical | no |

Source: [3.35.1 `gradle_utils.dart`](https://raw.githubusercontent.com/flutter/flutter/3.35.1/packages/flutter_tools/lib/src/android/gradle_utils.dart)
vs. the vendored copy at `flutter/packages/flutter_tools/lib/src/android/gradle_utils.dart:32-73,881`.

### Does 3.35.1 get any closer to JDK 25? No — not one step

**The Gradle cap is the binding constraint and 3.35.1 did not touch it.** Still `8.12`; Gradle 8.12
runs on Java 23 at most; Java 25 first runs on Gradle 9.1.0. 3.35.1 lifted only the *AGP* cap
(8.7.3 → 8.9.1), which is a different axis and does nothing for Java — AGP's own floor and default
is still 17 in every version shipped, 9.4.0 included. Its Java compatibility table is identical to
3.32's, entry for entry. **Upgrading his local Flutter from 3.32 to 3.35 buys exactly zero JDK-25 progress**, and
neither does any intermediate release before 3.44, which is where AGP 9 / Gradle 9 support lands.

**The JDK 21 recommendation is unchanged and is now the only path that works tonight.**

### Does the version skew itself hurt?

Mildly, and not in a way that blocks tonight:

- **The repo's pins are inside 3.35.1's caps**, so 3.35.1 builds this repo as-is: AGP `8.7.3`
  ( `android/settings.gradle.kts` ) ≤ 8.9.1, Gradle `8.12` ( `gradle-wrapper.properties` ) = cap.
  No warning, no migration prompt.
- **`pubspec.lock` is gitignored**, so the two machines resolve independently — the laptop against
  Dart 3.9.0, the dev server against 3.8.0. Contained, but it means a dep can be a different version
  on each side and nobody would see it in a diff.
- **`.metadata` still records 3.32.0's revision** (`be698c48…`), which is tracked. `flutter migrate`
  would reason from that base, so do not run it from the laptop while the skew stands.
- **`android/local.properties` is tracked and machine-specific**, and every `flutter build` rewrites
  it. Expect it to show as modified constantly; that is the tool, not a mistake.

The clean fix is to pick one Flutter and say so in the README. Not tonight's problem.

## Two gotchas that will stop a build regardless of Java

**`✗ Android license status unknown`** — his `flutter doctor` reports this, and it is an
*independent* blocker: the Android toolchain check fails on it whatever JDK is selected. Fix:

```bash
flutter doctor --android-licenses     # accept each prompt
```

Run it **after** pointing at JDK 21 — the licence tool runs on the selected JDK, so on 25.0.3 it can
fail on its own.

**`darwin-arm64 (Rosetta)`** — Flutter appends that when the machine is arm64 but `uname -m` in the
shell returns `x86_64`, i.e. the terminal itself is running translated
( `flutter/packages/flutter_tools/lib/src/base/os.dart:383-386` ). It is almost always a leftover
"Open using Rosetta" checkbox on Terminal.app. **It is not the cause of the `25.0.3` failure** and it
does not change any Java, Gradle or AGP compatibility above — the Java the build uses is chosen by
Flutter's JDK resolution, not by the shell's architecture. What it does cost is speed, since the
Dart tool and its artifacts run x64-translated. To clear it: uncheck *Open using Rosetta* in
Terminal's Get Info, or start the shell with `arch -arm64 zsh`, then re-run `flutter doctor -v`.

## How to check versions yourself

```bash
./flutter.sh --version            # the vendored SDK (this repo)
flutter --version                 # the laptop's own install — will differ (3.35.1 tonight)
flutter upgrade --verify-only     # shows what is available, changes nothing
flutter doctor -v                 # shows which JDK Flutter resolved
flutter analyze --suggestions     # Flutter's own Java/Gradle/AGP compatibility report

# what Java does Android Studio actually bundle on THIS machine?
"/Applications/Android Studio.app/Contents/jbr/Contents/Home/bin/java" -version
```

The repo's `flutter/` is excluded from the laptop rsync, so the first two commands answer about two
different SDKs. Check both before concluding anything.
