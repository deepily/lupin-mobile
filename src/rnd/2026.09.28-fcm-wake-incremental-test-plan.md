# 2026.09.28 — FCM wake-up: a minimal, incremental test plan

**Goal:** prove the **(a)** half of the expert's recommendation end to end, one small slice at a time. A push reaches a phone whose app has no socket, a notification **always** appears, and tapping it brings the app back with its socket reconnected. Live mode **(c)** gets its own plan once this works.

Inputs: [problem statement](2026.09.28-background-wake-socket-problem-statement.md) · [expert response](2026.09.28-background-wake-socket-problem-statement-response.md)

## What already exists (so nothing here is built from scratch)

- **Server:** `lupin/src/cosa/rest/fcm_wake_service.py` sends a data-only, high-priority `ws_wake` when a notification is queued for a user with **no live mobile WebSocket**. It sends at most one per 60 s, and today it is **disabled**: `FCM_SERVICE_ACCOUNT_JSON is not set`.
- **App:** token registration (`fcm_wakeup_service.dart`) and the background fetch → show → speak chain (`fcm_wake_chain.dart`). Both are compiled out unless the build passes `--dart-define=ENABLE_FCM=true`.
- **The natural trigger:** any notification sent to Rick's user (`target_user=…`) while the app has no socket. So we need no special "send a wake" tool; a short Python script that calls the existing notify API is enough.

## The slices

Each slice is small, has a single pass criterion, and doesn't start until the one before it passes.

| # | Slice | Who | Test | Pass means |
|---|---|---|---|---|
| 0 | **Server can send.** Firebase service-account key reachable from `lupin-rest-dev` via `FCM_SERVICE_ACCOUNT_JSON` (or `fcm wake auth mode = adc`), then bounce `:7999`. The key must belong to the **same Firebase project** as the app's `android/app/google-services.json`. | Rick | Read the boot log, and compare two JSON fields | The `[FCM-WAKE]` line says enabled, not `DISABLED`, **and** `project_id` in the service-account JSON equals `project_info.project_id` in `google-services.json` (today: `hello-world-foo-423219`). A key from another project also boots as enabled and fails only at send time with a SenderId mismatch, which would show up in slice 4 as a mysterious no-show *(María)* |
| 1 | **App registers.** `build-apk-on-server.sh --fcm` builds with `ENABLE_FCM=true`. It is opt-in until slice 4 proves the app still starts cleanly with FCM on, and only then becomes the default. Deploy and log in. | worker | Server log plus the token table | One `POST /api/fcm/register-token` 200 for the device; a row in the token repository |
| 2 | **Always show a notification** (the expert's C4). The four paths in `fcm_wake_chain.dart` that show nothing (no stored login, nothing undelivered, fetch error, any exception) post a fallback notification instead: "Lupin — new activity". A `ws_wake` never ends silently. Unknown message types stay ignored, since the server never sends them. | worker | **Unit tests**, one per path, each asserting `shown == true` | All four paths are green, and a negative control (fallback removed) goes red |
| 3 | **Tap reopens and reconnects.** Tapping the notification opens the app, and the app's normal start or resume path reconnects the socket. Likely already true; this slice is mostly a test. | worker | Widget test for the tap route, plus the server log in slice 4 | The server log shows a new mobile socket within seconds of the tap |
| 4 | **First end-to-end run, on the laptop emulator.** Use an emulator image with Google Play, signed in to a Google account. Launch the app and log in, then `adb shell am kill ai.deepily.lupin_mobile` so there's no socket. Send one notification to Rick's user. | worker + Rick's laptop | `adb logcat`, the server log, and a screenshot | The **real** notification text is on screen, and logcat shows `fetched 1` and `shown`, **not** `shown (fallback)`. The fallback would pass a weaker check, which is why this one names the text. The server log shows the send line for this wake, and the tap reconnects (slice 3) |
| 5 | **Swipe-away.** Same as 4, but swipe the app out of the recent-apps list instead of `am kill`. Never use **force-stop**: after a force-stop, FCM stays silent until the user reopens the app. That is documented Android behavior, not a bug. | worker + laptop | Same | Same |
| 6 | **Doze.** Same as 4, after `adb shell dumpsys battery unplug` and `adb shell dumpsys deviceidle force-idle`. | worker + laptop | Same, plus `dumpsys deviceidle get deep` = IDLE at send time | The notification appears **while** the emulator is idle, not after `unforce` |
| 7 | **Rick's phone on home Wi-Fi.** Repeat 5 and 6 on the phone, then leave it screen-off and unplugged for about an hour and send one notification. | Rick (a real-device concern only) | He looks at the phone | A notification within seconds, and the tap reconnects |

**Between sends, wait more than 60 s.** The server sends at most one wake per user per 60 s, so a second send inside that window proves nothing. Every pass in slices 4–7 includes the server's own send line for that wake. *(María's review, 2026-09-28.)*

**Stop here and reassess.** If slices 0–7 pass, the default path works, and the next plan covers live mode: the server's one-socket-per-phone rule with resume, and a `flutter_foreground_task` service of type `specialUse`.

## Deliberately NOT in this plan

- **Live mode (c)** and **the push-started service (b)**: next plan.
- **Speaking in the background.** The chain still speaks when the user's settings allow it. Android 17 will block that (the expert's C11), but whether it matters depends on the phone's Android version; check it in slice 7 (`adb shell getprop ro.build.version.release`). If it's 17, add a slice: speak only on tap.
- **Server contract changes** (`collapse_key`, TTL): optional, not needed to pass any slice.

## Where each slice can run

| Venue | Status | Note |
|---|---|---|
| Unit and widget tests (slices 2, 3) | Ready | `./flutter.sh test` on the server |
| Laptop emulator (slices 4–6) | Needs an image with Google Play | The easiest first venue: adb is already on the laptop, and the deploy script prefers the phone but falls back to an emulator |
| Server emulator | **Blocked**: `/dev/kvm` belongs to group `kvm`, and `rruiz` isn't in it | Would need `sudo usermod -aG kvm rruiz` plus a system image; only worth it if the laptop is inconvenient |
| Rick's phone (slice 7) | Ready | `deploy-apk-to-device.sh --build` |

## Estimated size

Slices 1–3: one worker, about half an evening (a build-script flag, a small fallback change, about six tests). Slices 4–6: about an hour, mostly waiting on the emulator. Slice 7: about an hour of the phone sitting idle.
