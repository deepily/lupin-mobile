# Plan — Agent Narration TTS via ElevenLabs (Option B, Client-Triggered)

## Context

Lupin Mobile now has foreground notification audio (commit `180a4ba`,
2026-04-21) using on-device `flutter_tts` for high/urgent notifications.
FCM/APNs push has been deferred indefinitely (see
`src/rnd/v0.1.7/2026.04.21-fcm-apns-push-considerations.md`), so the app
stays foreground-only.

The new requirement: **LLM/agent-generated text arriving over WebSocket
should be read aloud with ElevenLabs-grade voice quality.** Scope extends
beyond job status narration to longer descriptive passages about the work
being performed. Short notifications and extended narration should sound
identical (one voice, one quality tier).

### Decisions locked in (2026-04-21)

- **Option B pattern — client-triggered TTS.** The web client already
  uses this pattern: backend pushes text via WS notification event, the
  client decides (based on priority) to request TTS, then calls
  `/api/get-speech-elevenlabs` over HTTPS. Mobile adopts the identical
  pattern. Option D (server-auto-orchestration) is not needed now —
  round-trip latency is acceptable (~300ms time-to-first-audio on web).
- **Priority is the gate, no new field.** High/urgent triggers TTS,
  matching `notifications.js:5421`. No `should_speak` field added to
  `NotificationItem`; existing semantics are sufficient.
- **ElevenLabs primary, `flutter_tts` fallback.** Every spoken notification
  and narration flows through the ElevenLabs pipeline. `flutter_tts` is
  the fallback *only* when ElevenLabs is unavailable (quota exceeded,
  network error, `tts_error` event). Uniform voice quality when the
  primary path works; graceful degradation otherwise.
- **One voice at a time — FIFO queue.** Incoming speakable messages
  queue behind whatever is currently playing. Never double-voice.
- **Urgent preempts.** Urgent-priority messages interrupt the current
  utterance (do NOT resume it). After urgent finishes, the FIFO queue
  continues with the next pending item.
- **Event-name alignment.** Mobile renames its WS subscriptions to match
  backend emitter: `audio_streaming_chunk` / `audio_streaming_status` /
  `audio_streaming_complete` / `tts_error`. (Today mobile expects
  `audio_chunk` / `tts_start` / `tts_complete` — dead legacy.)
- **No ElevenLabs config customization yet.** Use defaults
  (`model_id=eleven_turbo_v2_5`, voice_id Rachel, `quality_profile=balanced`).
  Future work can expose per-context voice profiles.

## Existing Assets (from Phase 1 audit)

**Mobile (disabled but structurally intact):**
- `lib/services/tts/enhanced_tts_service.dart` — 1083 lines of streaming
  TTS player with `audioplayers`, public API `speak/pause/resume/stop`,
  event streams for status/buffer.
- `lib/services/websocket/websocket_event_handlers.dart:228–396` —
  `AudioEventHandler` with chunk buffering + playback controller.
- `lib/services/audio/audio_event_handler.dart` — complements the above.
- `lib/services/websocket/enhanced_websocket_service.dart` — dual-channel
  WS (queue + audio) that the TTS service was built for.
- DI stub note in `service_locator.dart:47-52` — nothing is actually
  broken; just tree-shaken out.

**Backend (already live in parent Lupin):**
- `POST /api/get-speech-elevenlabs` (routers/speech.py:433+) — takes
  `{session_id, text, voice_id, model_id, quality_profile, ...}`,
  returns 200 immediately, streams PCM 24kHz binary chunks to the WS
  session.
- WS events emitted: `audio_streaming_status` (loading/streaming),
  `audio_streaming_chunk` (binary frame), `audio_streaming_complete`,
  `tts_error` (with `error_code: quota_exceeded|rate_limit|auth_error|unknown`).
- Concurrency: one TTS stream per session; a new call replaces the old
  task (acts as server-side preempt).
- No explicit cancel endpoint (client disconnect handles it).
- ElevenLabs API key global, no per-user quota tracking.

**Web-client reference implementation:**
- `notifications.js:5421` — decides to queue TTS if `priority === "high" || "urgent"`.
- `notifications.js:5420-5440` — calls the TTS endpoint with a 500ms delay
  after ding to let the ding finish first.
- This is the exact behavior mobile will mirror.

## Architecture

```
Agent (backend, CoSA)
   │ emits NotificationItem with priority=high|urgent
   ▼
NotificationFifoQueue.push_notification()
   │ websocket_manager.emit_to_user_sync
   │   event="notification_queue_update"
   │   data={ notification: {..., priority, message, title, ...} }
   ▼
Mobile WS receives notification_queue_update
   │ lib/app.dart _dispatchWsEvent parses payload
   ▼
NotificationBloc._onExternalUpdate(notification)
   ├─ _refreshCurrent()                   (existing — inbox/conv refresh)
   └─ TtsOrchestrator.enqueueIfSpeakable(notification)  [NEW]
          │
          │ 1. Check priority ∈ {high, urgent}
          │ 2. Check user prefs (speakOnHigh / speakOnUrgent)
          │ 3. If urgent: preempt current, flush pending-before-urgent
          │ 4. Append to FIFO queue
          │ 5. If no current speaker, start next
          ▼
   TtsOrchestrator._speak(text)
          │
          │  IF fallback-mode active (from prior quota_exceeded):
          │     → NotificationAudioService.flutterTtsSpeak(text)
          │  ELSE:
          │     → POST /api/get-speech-elevenlabs
          │       { session_id, text, quality_profile: "balanced" }
          │       (async; returns 200 immediately)
          ▼
   Backend streams audio chunks to user's WS session
          │
          ▼
   EnhancedTTSService subscribes to audio_streaming_* events
          │ on audio_streaming_chunk → buffer + play via audioplayers
          │ on audio_streaming_complete → TtsOrchestrator._onSpeakDone() → advance queue
          │ on tts_error (error_code=quota_exceeded) →
          │    TtsOrchestrator._onElevenLabsQuotaExceeded() →
          │    switch to flutter_tts fallback for current + next N minutes,
          │    then retry ElevenLabs
          ▼
   User hears ElevenLabs voice
```

**Dings** (from `NotificationAudioService`'s existing channel-sound path)
stay as-is — the `lupin_{medium,high,urgent}.mp3` sound always plays
first via the Android notification channel. The ding is independent of
speech.

**Suppression rule**: while `EnhancedTTSService.isPlaying == true`, the
`NotificationAudioService.speak()` method returns early (no `flutter_tts`
call) to prevent double-voice. Dings still play since they route through
the OS notification channel, not the app's audio player.

### Phase 1 — Build slim `StreamingTtsPlayer` *(~3 hr)*

**Execution-time course correction (2026-04-21)**: After reading the
dependency chain, abandoned the "revive `EnhancedTTSService` as-is"
approach. That service depends on `EnhancedWebSocketService` (1776 lines),
`AdaptiveConnectionManager` (494), `AppLifecycleService` (437), and
`VoiceInputOutputService` — 2,707 lines of parallel WS infrastructure to
revive just to get a 1083-line player. And most of the 1083 lines are
adaptive-strategy / provider-metrics / cache logic that conflicts with
our "no config customization yet" decision. Cleaner to build a slim
purpose-built player against the already-live `WebSocketService` + `Dio`.

`EnhancedTTSService` + legacy deps stay tree-shaken on disk. Not deleted.
If the future brings a need for adaptive-strategy TTS, they're still
there as a reference.

**New file**: `lib/services/tts/streaming_tts_player.dart` (~250 lines).

**Responsibilities**:
- `speak(String text, {required String sessionId})` → POST
  `/api/get-speech-elevenlabs` via the shared `Dio` (auth interceptor
  already injects Bearer token). Returns immediately (backend starts
  streaming async).
- `handleWsEvent(String type, Map<String, dynamic>? data, Uint8List? binary)`
  — called by `lib/app.dart _dispatchWsEvent` when it sees a matching
  type. Routes:
  - `audio_streaming_status` → emits status events (loading / streaming)
  - `audio_streaming_chunk` → buffers + plays binary audio chunk via
    `audioplayers.AudioPlayer`
  - `audio_streaming_complete` → emits completion; orchestrator advances
    queue
  - `tts_error` → emits error with `error_code`; orchestrator handles
    quota fallback
- Exposes `Stream<TtsStatusEvent>`, `Stream<TtsCompleteEvent>`,
  `Stream<TtsErrorEvent>`, and `bool get isPlaying`.
- `stop()` — cancels current playback (used by urgent-preempt path).

**DI wire-up**:
- Register in `service_locator.dart` as a singleton in `_initializeServices()`.
- Constructor deps: `Dio` + internal `AudioPlayer`.

**`app.dart` routing**:
- Add three new cases in `_dispatchWsEvent`: `eventAudioStreamingStatus`,
  `eventAudioStreamingChunk`, `eventAudioStreamingComplete`, plus
  `'tts_error'`. Each calls `StreamingTtsPlayer.handleWsEvent(...)`.
- Handle binary audio chunks: today `_dispatchWsEvent` only decodes
  JSON strings. Backend sends audio as raw binary WS frames. The
  `WebSocketService.stream` emits whatever `web_socket_channel` yields
  (`String` for text, `List<int>`/`Uint8List` for binary). Need to
  teach `_connectWsToBlocs()` to pass through binary frames to
  `StreamingTtsPlayer` without trying to JSON-decode them.

**Session ID**:
- The WS session ID ("wise penguin" style) is stored on the
  `WebSocketService` instance (verified: `sessionId` getter exists).
  Orchestrator reads it at speak-time.

**Smoke test** (manual, user's laptop):
- Call `StreamingTtsPlayer.speak("Hello world", sessionId: ws.sessionId)`
  from a throwaway button or test harness after login.
- Verify ElevenLabs audio plays via the live backend.
- Log chunk count + total bytes to confirm streaming works.

### Phase 2 — `TtsOrchestrator` (FIFO queue + fallback + preempt) *(~3 hr)*

New file: `lib/services/tts/tts_orchestrator.dart`.

**Public API:**
```dart
class TtsOrchestrator {
  TtsOrchestrator({
    required EnhancedTTSService elevenLabs,
    required NotificationAudioService onDeviceFallback,
    required NotificationPreferences prefs,
    required String sessionId,  // WS session id, used for TTS endpoint
  });

  /// Called by NotificationBloc on every incoming notification.
  /// Decides speech-worthiness, queues, preempts, dispatches.
  void enqueueIfSpeakable({
    required String priority,
    required String message,
    String? title,
    required bool suppressDing,  // still respected: if true, skip speech too
  });

  bool get isPlaying;
  int get queueDepth;
  void stop();  // user-invoked cancel all
}
```

**Internal state:**
- `Queue<_Utterance> _fifo`
- `_Utterance? _current`
- `bool _elevenLabsDisabledUntil;` (Duration after `quota_exceeded`)

**Behavior contract:**
- `priority == "low"` or `"medium"` → ignored (no speech).
- `priority == "high"`: respect `prefs.speakOnHigh`; append to FIFO.
- `priority == "urgent"`: respect `prefs.speakOnUrgent`; if `_current`
  exists, call `elevenLabs.stopSpeaking()` and clear FIFO (do not
  resume); append urgent; start it.
- `suppressDing == true` → also skip speech (matches existing
  `NotificationAudioService` semantics; user intent is "silent mode for this item").
- Actually wait — web client semantics: `suppress_ding` silences the
  ding only, TTS still fires. Mobile should mirror. **Correction**:
  `suppress_ding` does NOT suppress speech. Re-verify against the web
  client impl before wiring.
- Listen on `elevenLabs.ttsCompletedStream` (or equivalent event) →
  remove `_current`, start next from FIFO.
- Listen on `elevenLabs.errorStream` → if `error_code == "quota_exceeded"`,
  set `_elevenLabsDisabledUntil = now + 5min`; speak the CURRENT utterance
  via `onDeviceFallback.flutterTtsSpeak()` instead; subsequent utterances
  also use fallback until window elapses; then retry ElevenLabs on the next.

Register in `service_locator.dart` as singleton; inject into
`NotificationBloc`.

### Phase 3 — Wire `NotificationBloc` to the orchestrator *(~1 hr)*

- `NotificationBloc` gains an optional `TtsOrchestrator? _tts` constructor
  param (same pattern as the existing `NotificationAudioService? _audio`).
- In `_onExternalUpdate(event)`, after calling
  `_audio?.handleIncoming(...)`, also call
  `_tts?.enqueueIfSpeakable(...)`.
- `NotificationAudioService.handleIncoming` gets a new guard: skip its
  own `flutter_tts.speak()` call when `_tts?.isPlaying == true` (avoid
  double voice) — though since the orchestrator now *is* the speech
  path, this is really about disabling the old hard-coded
  `flutter_tts` branch in `NotificationAudioService` entirely. The
  only case the orchestrator defers back to `flutter_tts` is the
  quota-fallback path, which goes through a new
  `onDeviceFallback.flutterTtsSpeak()` helper on
  `NotificationAudioService`.

Effectively: `NotificationAudioService` keeps dings; all speech moves
to `TtsOrchestrator`. The `flutter_tts` instance inside
`NotificationAudioService` becomes an internal fallback called only by
the orchestrator.

### Phase 4 — Tests *(~2 hr)*

- **Unit `tts_orchestrator_test.dart`** (primary focus, since this is
  the new logic):
  - Low/medium priority → no speech, queue empty.
  - High priority + speakOnHigh=true → enqueued + played.
  - High + speakOnHigh=false (prefs) → skipped.
  - Urgent preempts current high; queue cleared of previously-pending;
    urgent plays.
  - FIFO: two high notifications in rapid succession → second waits
    for first to complete.
  - Quota exceeded → next utterance plays via fallback; after 5min,
    retries ElevenLabs.
  - Master mute (from prefs) → all speech suppressed at orchestrator
    level.
- **Unit `enhanced_tts_service_test.dart`** (spot-check, since this is
  recovered-but-battle-tested code):
  - Verify renamed WS event subscriptions parse correctly.
  - Verify binary audio chunk routing to `audioplayers`.
- **Widget `notification_bloc_test.dart`** (extend existing):
  - New blocTest: external update with priority=urgent calls
    `tts.enqueueIfSpeakable` with correct args.

Mock `EnhancedTTSService` and `NotificationAudioService` in orchestrator
tests via `mocktail`.

## Out of Scope

- **Server-side orchestration (Option D)** — explicitly deferred.
  Revisit if 300ms+round-trip becomes a felt bottleneck.
- **New `should_speak` field** — not needed; priority already expresses
  speech-worthiness consistent with the web client.
- **ElevenLabs voice/config customization** — per-agent or per-context
  voice profiles, speed adjustments, etc. Use whatever defaults the
  `/api/get-speech-elevenlabs` endpoint already provides.
- **Cancel/replay UI** — future work. For now, user can mute via the
  existing `NotificationPreferences` screen.
- **FCM/APNs push** — already deferred, see
  `2026.04.21-fcm-apns-push-considerations.md`.
- **On-device Phase 5** execution in this session — we'll serialize
  the plan and run Phases 1–5 as a follow-on work item. Implementation
  hasn't started yet.
