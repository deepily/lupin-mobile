## Phase A — Shared fixture-capture library

Extract the HTTP + redaction helpers out of `capture-auth-fixtures.py` into a reusable module. Three domains earn it now; more will later.

### A1. Create `src/scripts/_fixture_lib.py`
- `post_json(base_url, path, body, headers=None) → (status, dict)`
- `get_json(base_url, path, headers=None) → (status, dict)`
- `write_fixture(fixture_root, relative_path, body)` — stable key order + 2-space indent
- `assert_no_jwt_residue(body, label)` — the naive 3-dot heuristic stays
- `redact_timestamp(value)` → `"2025-01-01T00:00:00+00:00"` if non-null
- `redact_tokens(tokens_dict)` → `access_token`/`refresh_token` replaced with stable placeholders

### A2. Rewrite `src/scripts/capture-auth-fixtures.py`
- Import from `_fixture_lib`, drop duplicated code.
- Same CLI, same env vars, same output fixtures — pure refactor.

### Verification
- `python src/scripts/capture-auth-fixtures.py` regenerates the auth fixtures; `flutter test test/unit/auth/` stays green.

## Phase B — Notifications fixtures

Endpoints with the highest drift surface (each is an envelope):
- `GET /api/notifications/senders-visible/{email}` → `List[SenderSummary]`
- `GET /api/notifications/conversation/{sender}/{email}` → `List[ConversationMessage]`
- `POST /api/notify/response` → `NotificationResponseAck`
- `POST /api/notifications/{id}/played` → `{status, notification_id}`

### B1. New `src/scripts/capture-notifications-fixtures.py`
- Log in (reuse auth flow).
- GET senders-visible with the authenticated user.
- If at least one sender exists: GET conversation for first sender; POST `played` for first message.
- No need to POST a real response (avoid side effects in a live backend) — fixture built from schema if necessary, but prefer a real capture where possible.
- Redact user email, sender ids, message ids, timestamps.

### B2. Convert `test/unit/notifications/notification_repository_test.dart`
- Swap the 5 existing hand-crafted stub Maps for `jsonBodyFromFixture(...)`.
- Keep the `notify()` test hand-crafted — it's testing query-param forwarding, not response parsing.
- Keep the `404 maps to NotificationApiException` test hand-crafted — deliberate bad shape.

### Fixtures produced
- `test/fixtures/notifications/senders_visible.json`
- `test/fixtures/notifications/conversation.json`
- `test/fixtures/notifications/notify_response_ack.json` (or a hand-constructed schema-faithful fixture if capture isn't possible)
- `test/fixtures/notifications/played_ack.json`

## Phase D — Broader TestKeys + two new widget tests (stretch)

Only start this after A/B/C are green. Stop cleanly if time runs out.

### D1. TestKeys additions in `lib/core/testing/test_keys.dart`
```dart
// Conversation
static const convRespondButtonPrefix = 'conv.respond.'; // + messageId

// Trust dashboard

static const trustDecisionApprove    = 'trust.decision.approve';

```

### D2. Apply keys to:
- `conversation_screen.dart` `_MessageCard` Respond button (`FilledButton.tonalIcon`)
- `interactive_prompt_sheet.dart` `_YesNoBody` Yes + No buttons
- `trust_dashboard_screen.dart` `_DecisionCard` per-decision container + approve/reject actions

### D3. New widget test — `test/widget/notifications/interactive_prompt_sheet_test.dart`
- Tests the sheet in isolation (conversation screen tests already cover the integration).
- Renders with `responseType: "yes_no"`, taps Yes via `TestKeys.promptYesButton`, asserts `NotificationsRespond` dispatched with `responseValue: "yes"`.

### D4. New widget test — `test/widget/decision_proxy/trust_decision_card_test.dart`
- Renders a single decision card with a mocked bloc.
- Taps approve → asserts `DecisionProxyRatify(approved: true, ...)` dispatched.
- Taps reject → asserts `DecisionProxyRatify(approved: false, ...)` dispatched.
