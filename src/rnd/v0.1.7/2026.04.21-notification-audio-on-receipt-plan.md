# 2026-04-21 — Notification Audio-on-Receipt (Ding + Speak) Plan

## Context

User requested: **"high-priority notification arrives → phone dings / speaks."**

Current state (verified 2026-04-21, commit `6d1d96e`):
- Mobile receives full `NotificationItem` payload over WS (`notification_queue_update`) — `message`, `title`, `abstract`, `priority` (`low|medium|high|urgent`), and `suppress_ding` are all already on the wire.
- **No audio plays on receipt.** `NotificationBloc._onExternalUpdate()` does a silent REST refetch; priority is decoded but never inspected; `suppress_ding` is parsed and ignored.
- `EnhancedTTSService` + `AudioEventHandler` exist (2025 Phase 4.5) but are wired to Claude Code chat TTS, not notifications.
- **Backend has no FCM/APNs integration** (`firebase_admin` appears only as commented-out example code in `src/cosa/rest/auth.py`). Off-screen audio requires backend work first — that's a parent-Lupin plan item, not this plan.

Mobile can ship the **foreground** path unilaterally. Background requires backend work to land first.

## Goals (In Scope)

1. **Foreground ding**: High-priority or urgent notification arriving while the Lupin Mobile app is active plays a configurable notification sound, honoring `suppress_ding`.
2. **Foreground speech**: Urgent notifications additionally speak the `title` + `message` text using device TTS (no backend TTS call for MVP).
3. **User settings**: A Settings entry to toggle dings and speech globally, and per priority level.
4. **Android-first**: Android is the target platform (per project CLAUDE.md). iOS parity is a follow-up.

## Non-Goals (Deferred)

- **Off-screen / background notifications**: Requires FCM (Android) + APNs (iOS) on the backend. File as parent-Lupin item (see Cross-Repo Dependency section).
- **Backend-streamed ElevenLabs TTS**: `/api/get-speech-elevenlabs` exists but unwiring the orphaned `EnhancedTTSService` for notifications adds scope and $ cost. Device TTS (`flutter_tts`) is free, offline, and fine for terse notification text. Revisit if voice quality complaints arrive.
- **iOS**: Out of scope for MVP. `flutter_local_notifications` + `flutter_tts` both support iOS so the eventual lift is modest, but not this plan.
- **Quiet hours / do-not-disturb schedule**: Nice-to-have follow-up. User's OS-level DND already suppresses notification sounds.

## Decisions (locked 2026-04-21 by user)

1. **TTS source**: `flutter_tts` on-device. No backend ElevenLabs hookup in this scope.
2. **Priority policy** (see table below): low=silent, medium=single ding, high=single ding + speak, urgent=single ding (distinct alert tone) + speak. Speech defaults **ON** for high and urgent. Aligned to Lupin web client — no double-ding.
3. **Sound assets**: the three MP3 files from the Lupin web client's `static/audio/notification-{medium,high,urgent}-priority-v2.mp3`, copied into `android/app/src/main/res/raw/` as `lupin_{medium,high,urgent}.mp3`. Same audio identity as web.
4. **Speech voice**: device default. No language selector UI in MVP.
5. **Truncation**: speak `"${title}. ${message}"` — no length cap in MVP; revisit if long research-style messages get annoying.
6. **Settings storage**: `SharedPreferences`.
7. **Ingress**: single — extend `NotificationsExternalUpdate` to carry the parsed `NotificationItem`. Reevaluate after Phase 2 if the single-ingress pattern gets noisy.

## Priority → Audio Behavior

**Aligned to Lupin web client** (`src/fastapi_app/static/js/notifications.js:1354-1404,5374-5440`). Same three sound files, same TTS tiers, same `suppress_ding` honor, same 300ms gap between ding and TTS.

| Priority | Ding | Speech | Android channel | Sound asset | Default-on? |
|---|---|---|---|---|---|
| `low`    | — | — | (none — no audio path) | — | n/a |
| `medium` | single | — | `lupin_medium` / `Importance.default` | `res/raw/lupin_medium.mp3` | ding: yes |
| `high`   | single | title + message via `flutter_tts`, 300ms after ding | `lupin_high` / `Importance.high` | `res/raw/lupin_high.mp3` | ding: yes · speak: **yes** |
| `urgent` | single (distinct alert tone) | title + message via `flutter_tts`, 300ms after ding | `lupin_urgent` / `Importance.max` | `res/raw/lupin_urgent.mp3` | ding: yes · speak: **yes** |

All behavior gated by `NotificationItem.suppress_ding` (backend-sent — when true, ding is suppressed; the web client still speaks for high/urgent even when dinged is suppressed, so mobile mirrors that) and per-user `NotificationPreferences` toggles.

Note on `suppress_ding` semantics (from web client `notifications.js:5408`): `suppress_ding` silences the *ding* only. TTS speech for high/urgent still fires unless `speakOnHigh`/`speakOnUrgent` preference is off, or master-mute is on.

## Sound Assets

**Reused from Lupin web client** — maintains audio identity across platforms and avoids asset-drift risk.

- Source: `src/fastapi_app/static/audio/notification-{medium,high,urgent}-priority-v2.mp3` (48–62 KB each).
- Destination in mobile repo: `android/app/src/main/res/raw/lupin_{medium,high,urgent}.mp3` (renamed for Android resource-naming rules: lowercase + underscore, no hyphens).
- Assets copied 2026-04-21 during Phase 0. If the web team updates the assets later, the mobile repo needs a copy-over (consider scripting `src/scripts/sync-notification-sounds-from-lupin.sh` as a follow-up).
- Registered on each channel via `sound: RawResourceAndroidNotificationSound('lupin_medium' | 'lupin_high' | 'lupin_urgent')`.

## Architecture

```
WebSocket message
  │
  ▼
lib/app.dart  _dispatchWsEvent
  │  eventNotificationQueueUpdate
  ▼
NotificationBloc.add( NotificationsExternalUpdate( notification: NotificationItem? ) )
  │                                                ▲
  │                                                └─ NEW: pass the payload, not just a ping
  ▼
NotificationBloc._onExternalUpdate
  ├─ _refreshCurrent( emit )         (existing)
  └─ _maybePlayAudio( notification ) (NEW)
         │
         ▼
NotificationAudioService (NEW)
  ├─ reads NotificationPreferences (NEW, SharedPreferences-backed)
  ├─ skips if suppress_ding == true
  ├─ skips if priority < threshold
  ├─ shows flutter_local_notifications ding (high + urgent)
  └─ calls flutter_tts.speak("<title>. <message>") (urgent only)
```

**Key design choice — single ingress**: `NotificationsExternalUpdate` already fires once per WS event. Extending its payload to carry the full `NotificationItem` keeps the audio trigger on the same code path, so we don't duplicate WS dispatch in `app.dart`.

### Phase 1 — Foreground dings, all three channels *(~2.5 hr)*

- Add deps: `flutter_local_notifications: ^17.2.3` and `shared_preferences: ^2.3.2` to `pubspec.yaml`.
- Android manifest: add `POST_NOTIFICATIONS` permission (API 33+).
- ✅ Sound assets in place: `res/raw/lupin_{medium,high,urgent}.mp3` (copied from web client in Phase 0).
- Create `lib/services/notification_audio/notification_audio_service.dart` — owns the `FlutterLocalNotificationsPlugin` singleton; exposes `initialize()`, `playDing({required String title, required String body, required String priority})`.
- Register three Android notification channels at `initialize()`: `lupin_medium` / `lupin_high` / `lupin_urgent` with importance levels per the priority table; each channel uses its matching `RawResourceAndroidNotificationSound('lupin_<priority>')`.
- Create `lib/services/notification_audio/notification_preferences.dart` — `SharedPreferences`-backed toggles: `dingOnMedium`, `dingOnHigh`, `dingOnUrgent`, `speakOnHigh`, `speakOnUrgent`, `masterMute`.
- Extend `NotificationsExternalUpdate` event: new optional `notification` field carrying the parsed `NotificationItem` when WS event decodes one.
- `app.dart _dispatchWsEvent`: when `notification_queue_update` arrives with a `notification` key, parse via `NotificationItem.fromJson` and pass into the bloc event.
- `NotificationBloc._onExternalUpdate`: add `_maybePlayAudio( item )` call before `_refreshCurrent`.
- `_maybePlayAudio` logic (aligned to web client semantics):
    - Early-return if `masterMute` is true.
    - Ding: skip if `suppress_ding` is true OR the per-priority `dingOn*` toggle is false. Otherwise pick channel by priority.
    - Speech: skip if priority not in `{high, urgent}` OR the matching `speakOn*` toggle is false. Otherwise schedule `flutter_tts.speak(...)` with a 300ms delay to let the ding finish.
- DI wiring in `service_locator.dart`: register `NotificationAudioService` + `NotificationPreferences` as singletons; init the audio service at app startup in `main.dart`.

### Phase 2 — Foreground speech on high + urgent *(~1 hr)*

- Add dep: `flutter_tts: ^4.2.0`.
- Extend `NotificationAudioService`: add `speak(String text)` using `FlutterTts` singleton; default voice/rate/pitch.
- The speech trigger logic was already scoped in Phase 1's `_maybePlayAudio`; Phase 2 fills in the `speak()` implementation and deps, then the dispatch call becomes live.
- Dispatch pattern: ding is async (OS-managed via the notification channel); speech fires after a `Future.delayed(300ms)` so the ding audio plays cleanly without overlap. Same timing as web client.
- Text format: `"${title}. ${message}"` when title non-empty, else just `message`.

When unblocked, the mobile work is:

**Deps + native config**:
- `firebase_core` (^3.6.0 or latest stable)
- `firebase_messaging` (^15.1.3 or latest stable)
- `android/app/build.gradle` + `android/build.gradle`: apply Google Services plugin
- `android/app/google-services.json` — from Firebase console, gitignored (per-environment)
- `android/app/src/main/AndroidManifest.xml`: no extra perms needed (FCM uses our existing `POST_NOTIFICATIONS`)
- `main.dart`: call `await Firebase.initializeApp()` before `ServiceLocator.init()`
- Register the top-level background handler via `FirebaseMessaging.onBackgroundMessage(...)` (must be top-level per FCM — not a method on a class)

**New files**:
- `lib/services/push/fcm_service.dart`: singleton that listens for `AuthBloc` state, registers/unregisters device token with backend
- `lib/services/push/fcm_background_handler.dart`: top-level function annotated `@pragma('vm:entry-point')`. Parses FCM `data` payload (priority, message, title, suppress_ding) and routes through `NotificationAudioService.handleIncoming(...)`. **Critical**: must NOT parse the `notification` FCM field — the backend must dispatch as `data`-only per the cross-repo spec. If `notification` field is populated, Android renders it opaquely and our priority logic is bypassed.

**Auth flow hooks**:
- After `AuthAuthenticated`: call `FcmService.registerToken(userEmail)` → `POST /api/devices/register`
- Before `AuthUnauthenticated`: call `FcmService.unregisterToken()` → `POST /api/devices/unregister`
- On `onTokenRefresh` stream: re-register with the rotated token

**Test strategy**:
- Unit test for `FcmService` token registration/unregistration with mocked Dio
- Unit test for `fcm_background_handler` routing — mock `NotificationAudioService`, verify priority extraction from `data` payload and correct dispatch
- Cannot automate end-to-end FCM delivery test (requires real Firebase project + real device) — rely on operator's laptop + emulator smoke test

**Known risks**:
- FCM background handlers have a strict time budget (~20s on Android). Keep the dispatch lean — no heavy allocation, no synchronous HTTP.
- FCM payloads have a 4KB size cap. Backend must truncate `message` + `abstract` if long, and mobile's speech must fall back gracefully to whatever fits.
- Device token rotation: tokens change on app reinstall, OS update, manual clear. `onTokenRefresh` handler must re-register or user will silently stop receiving pushes.
- Foreground + background dual delivery: when the app is foregrounded AND receives both a WS event AND an FCM push for the same notification, the user would hear the ding twice. Mitigation: in the foreground `onMessage` handler, dedupe by `notification.id` against a short-lived in-memory set, OR simply ignore foreground FCM since the WS path already handles it (preferred — simpler).

## Risk / Unknowns

- **`flutter_local_notifications` API surface churns across major versions**: pin to the specified version in Phase 1; don't chase `^`.
- **Notification channel config persists after uninstall/reinstall on some Android versions**: adding a new channel works; editing an existing channel's sound requires a new channel ID. Not a concern on first install.
- **`flutter_tts` voice selection is OEM-dependent**: some devices have minimal Google TTS, some have Samsung TTS; behavior will vary. Don't promise exact voice — rely on OS default.
- **Default-on speech on high could surprise first-time users**: mitigated by settings master-mute toggle prominently placed on the settings screen.
- **Web-client parity cross-check is a prerequisite**: Phase 0 includes a grep of the Lupin web UI to confirm this tier table matches the existing user mental model. Any mismatch aligns mobile to web, not the other way around.
