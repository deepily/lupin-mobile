## The architecture mapping — §5

### B1 · MAJOR · §5 line 92 — repositories are pointed at the wrong directory

**Claim**: the web's `*Store.ts` becomes a "Repository" living in `lib/core/repositories/`.

**Found**: every feature repository written since this app adopted the feature-first layout lives in `lib/features/<feature>/data/`. Six of them:

```
lib/features/agentic/data/agentic_repository.dart
lib/features/claude_code/data/claude_code_repository.dart
lib/features/decision_proxy/data/decision_proxy_repository.dart
lib/features/docs/data/doc_repository.dart
lib/features/notifications/data/notification_repository.dart
lib/features/queue/data/queue_repository.dart
```

`lib/core/repositories/` holds something different: five cross-cutting CRUD abstractions (`audio`, `job`, `session`, `user`, `voice`) plus an `impl/` folder, all dated 16 April and all listed in the barrel at `lib/core/repositories/repositories.dart`. It is the pre-feature-layout tier. **Nothing under `lib/features/` extends any of it** — `grep -rn 'extends BaseRepository\|extends CachedRepository' lib/features lib/services` returns zero hits.

**Receipts**: `lib/core/repositories/base_repository.dart:7` (`abstract class BaseRepository<T, ID>` — pure CRUD, no HTTP), `lib/core/repositories/repositories.dart` (barrel, five legacy entries), `lib/features/docs/data/doc_repository.dart:19`.

**What breaks, for whom, when**: whoever builds Phase 0 puts five new repositories in the one directory the house pattern walked away from, `lib/core/repositories/` acquires a second incompatible meaning, and the next person cannot tell which tier a new repository belongs in. It surfaces at the first code review, not at runtime — which is why it needs fixing in the plan rather than in the build.

**Fix**: `lib/features/<pane>/data/<pane>_repository.dart`.

|---|---|---|

### B3 · MAJOR · §5 table — the BLoC layer is missing from the plan entirely

**Claim**: three layers — Repository, Model + mapper, Widget.

**Found**: this app is BLoC-driven throughout. Eleven features carry a `domain/` bloc triad (B2's table shows five of them). The word "Bloc" appears **zero times** in the plan as a layer; the single grep hit at line 169 is the label "Blocked by".

This is not a naming quibble. The plan's own Phase 0 list, and §6 line 138, put four things in the build that have nowhere to live under a Repository→Model→Widget map:

- the per-pane polling timer,
- the `AppLifecycleState.paused` stop and the refresh-once-on-resume,
- the failed-write retry under ruling 2,
- pane state generally (loading, empty, error).

And §10 line 298 already points at the right home for the fourth without naming the layer: commit `a8c30b3` put the unsent-answer retry in `lib/features/focus_mode/domain/focus_chat_bloc.dart` (+46 lines) with its UI half in `presentation/focus_chat_pane.dart` (+46). So **§5 and §10 describe different architectures**, and §10 is the one that matches the repo.

**Fix**: add the row — `state · timer · lifecycle · retry` → `lib/features/<pane>/domain/<pane>_bloc.dart` — and say Phase 0 ships a BLoC base or mixin for the lifecycle-aware polling rather than five copies of it.

### B4 · MAJOR · §5 line 96 — the two features named as the pattern do not set it

**Claim**: "each following the pattern `focus_mode/` and `docs/` already set."

**Found**: those are the only two features that depart from the common shape, and they depart in opposite directions.

- `lib/features/focus_mode/` — `domain/` + `presentation/`, **no `data/`**. Its repository-equivalent work sits in the bloc.
- `lib/features/docs/` — `data/` + `presentation/`, **no `domain/`**. No bloc at all.

Between them they set no pattern; nine other features do. Citing these two is what produced B1 and B2 — `docs/` puts its repository in `data/`, which is the opposite of what §5's own table says.

**Fix**: cite `queue/` or `notifications/` — full three-layer, bloc-driven, and `queue/` is the closest analogue to a task pane that already exists.

### B5 · MAJOR · §10 line 291 (and Phase 0) — 401 handling already exists one layer up

**Claim**: the integration tier covers "the repository hits a mocked endpoint, **handles a 401**"; Phase 0 builds a "repository base" that does so.

**Found**: 401 is handled globally by a Dio interceptor registered in the service locator, and the house rule is that repositories do not touch credentials at all. The `docs` repository says it in its own docstring:

> *"The auth interceptor registered in `service_locator.dart` injects the Bearer token and refreshes on 401, so nothing here touches credentials."*
> — `lib/features/docs/data/doc_repository.dart:10-12`

**Receipt**: `lib/services/auth/auth_interceptor.dart:42` (`final isAuth = response?.statusCode == 401;`).

**What breaks**: a repository base that also handles 401 gives the app two refresh paths on the same response. Best case it is dead code; worst case both fire and the second refresh races the first, which is the kind of bug that only shows up on a flaky connection — a phone.

**Fix**: strike 401 from Phase 0 and from the integration tier. Keep the other half of line 291 — "handles an empty `not_approved` result without mistaking it for an error" is a real test and nothing existing covers it.

## The shared-row invariant — §7 and §10

### B6 · MAJOR · §7 lines 155–171 — the one-row rule is recommended, not guaranteed

**Claim** (line 171): *"Build one `TaskRow` widget driven by one schema constant, and let Task List, Holding Area and Finished Tasks all render it."*

That is an instruction. It is not a mechanism, and §7 supplies no other. The following satisfies every word of §7, passes §10's test, and is what a developer under deadline will actually write when the Holding Area needs its selection checkbox:

```dart
TaskRow( model: row, pane: Pane.holdingArea )   // ← one widget, three behaviours
```

One widget type. One schema constant. Three divergent layouts, reached by `if (pane == …)` inside the build method. The web comment §7 quotes does not protect widget identity, it protects **"cell-for-cell row identity between panes"** — and a shared type delivers no part of that.

**What breaks, for whom, when**: Rick, who asked for this specifically, opens the Holding Area three months from now and a column is in a different place than in the Task List. Nothing went red. The failure arrives quietly and late, which is exactly what the web comment exists to prevent.

**Fix — one sentence in §7 turns the recommendation into a mechanism**: `TaskRow`'s constructor takes a row model and the `ROW_SCHEMA` constant, **and no pane-discriminating parameter of any kind**. Anything a pane needs that its siblings do not — the Holding Area's batch selection, the Finished Tasks glyph — lives in the group header or in a wrapper around the row, never in a branch inside it. Drift then requires changing the constructor, which is visible in review; today it requires adding an enum case, which is not.

### B7 · MAJOR · §10 line 297 — the guard test misses the drift it is aimed at

**Claim**: *"All three task panes render the same row widget type. The guard on §7 — without it, the drift the web source warned about happens silently."*

`find.byType(TaskRow)` in all three panes. Concretely, here is what passes that test while drifting:

1. **A `pane:` parameter branching inside the widget** (B6). One type, three layouts. Green.
2. **Different field subsets passed to the same widget** — Finished Tasks omits `priority`, Task List keeps it. Same type, different cells. Green.
3. **A bespoke row for a special case** — the Holding Area renders `TaskRow` for ordinary rows and `_BatchSelectableRow` for selected ones. `find.byType` finds at least one `TaskRow` and passes. Green.
4. **A wrapper** — a pane wraps `TaskRow` and appends its own trailing actions. The type is still present. Green.

Number 1 is the one I would bet on, because a shared widget under feature pressure grows branches rather than forks.

**Fix**: assert the rendered cells, not the widget type. Render one fixed row model through all three panes and assert they produce the **identical ordered list of cell keys**. This repo already has the machinery for that: `lib/core/testing/test_keys.dart` (248 lines) is a single source of truth for stable widget keys, written precisely so selectors survive UI churn — and the plan never mentions it. Keep §10's `ROW_SCHEMA` field-list pin (line 289); it is the right test and it is complementary.

### B8 · MAJOR · §7 lines 164–177 — line 1 does not survive 360 dp

**Claim**: line 1 of the row carries `id · title · class · status · priority`, with an ellipsis right-justified on the title line (line 177).

**Found**: that is five fields plus a control on one line of a phone. The arithmetic at 360 dp, the ordinary Android portrait width:

| | dp |
|---|---|
| Screen | 360 |
| less 16 dp gutters | 328 |
| less the ellipsis target — `kMinInteractiveDimension = 48.0` | 280 |
| less `id`, 8 hex chars at 12sp monospace | ≈ 222 |
| less `class` | ≈ 174 |
| less `status` chip | ≈ 110 |
| less `priority` (`P1`) | ≈ 86 |
| **left for `title`** | **≈ 86 dp — about 12 characters at 14sp** |

Twelve characters. The titles in this fleet run past a hundred and share a `[LUPIN-MOBILE] Phase N:` prefix, so **every row in the Task List truncates to the same string** and the pane cannot be read at all.

**Receipts**: `flutter/packages/flutter/lib/src/material/constants.dart:27` for the 48 dp floor; `lib/features/docs/presentation/doc_panel.dart:23` — this app's own narrow/wide threshold is `docPanelSplitWidth = 600`, so 360 is squarely phone territory by the repo's existing definition.

**It gets worse with an accessibility setting on.** The app applies no text-scale clamp — `grep -rn 'textScale\|TextScaler' lib` returns nothing, so the OS font-size setting passes through at full strength, which is correct behaviour and should stay. At the large-font settings a low-vision user actually runs, the title falls to roughly six characters.

**Fix**: line 1 on a phone is `title` and the ellipsis, full stop. `id`, `class`, `status` and `priority` move to line 2 or become a glyph row beneath the title. The three-line model survives; the five-fields-on-line-1 packing does not. This is a genuine phone-versus-desktop divergence and, like §12's `char_budget`, it deserves to be called out rather than discovered.

## Accessibility

### B9 · MAJOR · §7 line 183 — half of a both-or-broken pairing was carried across

**Claim**: *"On web the state lives in `aria-expanded` **and** the `hidden` attribute — both, because either alone produces a pane that is broken for one class of user while looking fine to the other. The Flutter equivalent is a real `Semantics(expanded: …)` on the toggle, not just a visual rotation."*

The document states the both-or-broken rule correctly and then names the Flutter analogue of **only the first half**. `hidden` has an analogue too, and it is not automatic: when the row is collapsed, the controls must be **absent from the semantics tree**, not merely invisible.

Under ruling 2 this is not academic. Line 185 says it plainly — the disclosed row is the pane's primary verb surface. If the collapsed controls are hidden with `Opacity(opacity: 0)`, a clipped `SizedBox(height: 0)`, or `Visibility(…, maintainSemantics: true)`, then TalkBack reads and can **activate** every row's write verbs while that row is visually collapsed. A sighted user sees a tidy list; a screen-reader user hears approve and won't-fix on every row and can fire them.

**Adversarial note, and it is why this is MAJOR and not BLOCKER**: the two idioms a Flutter developer reaches for first — `Visibility(visible: false)` and `Offstage` — both drop the child from the semantics tree by default. The likeliest implementation is accidentally correct. The finding stands because the plan specifies the `aria-expanded` half explicitly and leaves this half to luck, and because "accidentally correct" is the precise condition under which something later drifts without anyone noticing.

**Fix**: one clause in §7 — collapsed controls are removed from the tree, not hidden in place; `Visibility` or `Offstage`, never `Opacity` or a zero-height box; and a widget test that asserts no action node is reachable while collapsed.

### B10 · ✅ the API claim is correct — §7 line 183, verified in the pinned toolchain

`Semantics(expanded:)` is real and is the right call. Verified in the SDK this repo vendors — Flutter 3.32.0 stable, Dart 3.8.0:

- `flutter/packages/flutter/lib/src/widgets/basic.dart:7344` — `bool? expanded` on the `Semantics` constructor.
- `flutter/packages/flutter/lib/src/semantics/semantics.dart:1392` — the field: *"If non-null, indicates that this subtree represents something that can be in an 'expanded' or 'collapsed' state."*
- `flutter/packages/flutter/lib/src/semantics/semantics.dart:5401-5405` — setting it raises `SemanticsFlag.hasExpandedState` and `SemanticsFlag.isExpanded`.

Those two flags are what the Android engine turns into the expandable state on the accessibility node, so **TalkBack appends "expanded" or "collapsed" when the row takes focus, and announces the new state after a toggle**. That is exactly the `aria-expanded` behaviour, and the plan is right that a visual rotation would deliver none of it.

Two caveats worth adding to §7, neither of which contradicts the claim:

1. **`expanded:` carries state, not purpose.** It announces *that* something is collapsed, never *what* opens. The toggle is an ellipsis — a glyph has no accessible name — so without `Semantics(label: …)` TalkBack says "button, collapsed" and the user never learns there are verbs behind it. On the web the ellipsis presumably inherits an accessible name from its markup; here it must be supplied.
2. **This would be the first `Semantics` widget in the app.** `grep -rn 'Semantics(' lib --include=*.dart` returns **zero** across the entire codebase. There is no existing accessibility practice for §7 to "carry the substance across" into — it is being established from nothing, on the pane set that also happens to be the app's densest UI. That is a larger Phase 0 item than one line of §7 conveys, and it is worth Tiffany knowing before she scopes it.

### B11 · MINOR · §6 line 140 — pull-to-refresh cannot be triggered by a screen reader

**Claim**: *"Pull-to-refresh should be there too, on every pane, regardless — it is the gesture a phone user will reach for, and it costs almost nothing."*

**Found**: `RefreshIndicator`'s only accessibility surface is `semanticsLabel` / `semanticsValue`, and both describe the spinner once a refresh is already running — `flutter/packages/flutter/lib/src/material/refresh_indicator.dart:158-159` and `:287-289`. There is **no semantic action that invokes the refresh**, and the pull itself is a drag TalkBack does not pass through to the app. A screen-reader user cannot refresh.

**Adversarial, and it is why this is MINOR rather than MAJOR**: it does not strand anyone. §6's foreground poll still refreshes every 60 s on its own, so the data arrives without the gesture — the user loses "refresh now", not "refresh". And it is a **pre-existing gap in this app, not one the plan introduces**: `RefreshIndicator` is already the house pattern across six-plus screens, and none of them pairs it with a button — `lib/features/notifications/presentation/inbox_screen.dart:41` carries only "Clear all".

Raised anyway because these are the first screens whose whole point is fleet state someone is actively waiting on, which makes them the right place to add an app-bar refresh and set the pattern.
