# Getting the WebSocket back after an FCM wake-up on Android 14–17 (Flutter, sideloaded)

Build a hybrid of **(a) and (c)**. Every `ws_wake` should always post a user-visible notification: fetch it over HTTP, and let a tap reopen the app, which reconnects. Separately, offer an opt-in **"live mode"** that runs as a long-lived foreground service, started from the UI and never from the push handler. Treat **(b)** — starting a foreground service from the FCM handler — as an optional experiment, not the backbone. On Android it is allowed, but only within a brief, undocumented window. The window closes when FCM deprioritizes the message, and a Flutter background isolate makes it easy to miss.

## TL;DR

- **Recommendation: a + c.** Treat each wake-up as "show a notification now, reconnect on tap". Add a user-toggled "live mode" foreground service that owns the only socket while it is on. It uses the `specialUse` type (or `remoteMessaging`), not `dataSync`: Android Developers' *Foreground service timeouts* page says dataSync services may "run for a total of 6 hours in a 24-hour period", with the limit "shared by all of an app's foreground services of the specified type". The app is sideloaded, so Play policy review does not apply, but every OS runtime rule still does.
- **The rules that decide it:** starting a foreground service from the background is banned since Android 12, apart from a *brief* exemption for high-priority FCM. That exemption is lost if the message was downgraded, and FCM downgrades high-priority messages that don't produce a visible notification. `onMessageReceived` gets only "several seconds". Android Developers' *Foreground service types* page says `shortService` "can only run for a short period of time (about 3 minutes)", counted from `startForeground()`. Android 16 tightened job quotas, and Android 17 restricts background audio. That last rule directly affects speaking TTS from the push handler.
- **Architecture:** one owner per socket at any moment. The service's `TaskHandler` owns it in live mode and the UI isolate owns it otherwise. The two sides talk over `flutter_foreground_task`'s data ports, and the server enforces "one connection per (user, device); a new connection supersedes the old", with sequence-number resume. Use `flutter_foreground_task` 11.x, published Sep 2026 and actively maintained.\[1\] Avoid `flutter_background_service`: 5.1.0, Dec 2024, with open Android 15 and wakelock-drain issues.\[2\]

## 1. Executive recommendation and rationale

| Priority | Mechanism | When |
|---|---|---|
| Default | **(a+)** FCM wake → background isolate fetches over HTTP → **always** posts a local notification (with a fallback text if the fetch fails) → tap opens the app → UI isolate reconnects the WebSocket and resumes from the last sequence number | Always on |
| Opt-in | **(c)** "Live mode": a foreground service with a persistent notification, **started from a visible activity**, owning the single WebSocket | User toggles it; e.g. during an active agent session |
| Experimental | **(b)** FCM handler starts a `shortService` foreground service (≤3 min) to drain traffic | Only after (a) and (c) are solid, only if the delivered priority is still HIGH, with a fallback to (a) |
| Rejected | Background socket without a foreground service; WorkManager periodic polling; a cloud relay | — |

Why:

1. **(a) is the only path that stays compliant and reliable over time.** High-priority FCM is meant to produce a user-visible notification. If FCM sees a pattern of high-priority messages that don't, it deprioritizes them to normal.\[3\] Normal-priority messages are held while the device is in Doze.\[4\]\[5\]\[6\] The current handler already shows a notification. The fix is to make that **unconditional**, and to add a tap target.
2. **(c) is the only way to keep traffic flowing continuously and in real time while the phone is idle.** A foreground service keeps the process at foreground-service priority. The official Doze/App Standby docs list "a process currently in the foreground (either as an activity or foreground service)" as an exemption.\[7\] Starting it from the UI avoids the background-start ban entirely.
3. **(b) is fragile in exactly this stack.** The exemption is "brief" and has no published duration.\[8\] A Flutter background isolate needs time to spin up an engine before Dart can call anything, and debug (JIT) builds make that slower. If the message was downgraded, the start throws `ForegroundServiceStartNotAllowedException`.\[9\] It adds about 3 minutes of live traffic per wake — useful, but not worth the complexity until (a) and (c) work.
4. **Keep the server contract as is**: data-only, no content, high priority, ≤1 per 60 s. Two optional, content-free additions: `collapse_key: "ws_wake"` and a short TTL. The contract doesn't need to change, because the *client* guarantees the visible notification.

## 2. The Android constraints that decide it

**C1 — Background start of a foreground service is banned (API 31+), with an FCM exemption.** "Beginning with Android 12 (API level 31), apps are not allowed to start foreground services while the app is running in the background, with a few specific exemptions… the system throws `ForegroundServiceStartNotAllowedException`."\[8\] One listed exemption is "Your app receives a high priority message using Firebase Cloud Messaging."\[9\] (Android Developers, *Restrictions on starting a foreground service from the background*.)\[9\]

**C2 — The exemption disappears if FCM downgraded the message.** "If the message's priority is downgraded, your app cannot start a foreground service and attempting to start one results in a `ForegroundServiceStartNotAllowedException`. So, it's recommended to check the result of `RemoteMessage.getPriority()` and confirm it's `PRIORITY_HIGH()` before attempting to start a foreground service."\[9\] (Same page.)\[9\]

**C3 — The exemption is short.** "There is a brief exemption if your app launches a foreground service in response to a high-priority FCM message. If you don't launch the service quickly enough, you get a `ForegroundServiceStartNotAllowedException`. Specific exemptions sometimes become more restrictive with new Android releases."\[8\] (Android Developers, *Troubleshoot foreground services*.) Google publishes no number. microG, an open-source Play-services reimplementation, grants its temporary allowlist for **10,000 ms** ("GCM Push").\[10\] Treat that figure as an informed guess about Google's behaviour, not a documented fact. AOSP also has a `push_messaging_over_quota_behavior` setting that Google Play services can change remotely.\[11\] Its default of 1 corresponds to "temp-allowlisted, but foreground-service start not allowed" for over-quota pushes.\[12\]

**C4 — FCM deprioritizes high-priority messages that don't produce a visible notification.** "If FCM detects a pattern in which messages don't result in user-facing notifications, your messages may be deprioritized to normal priority or delegated for handling by Google Play services… If the user has disabled the notification permission for your app, none of your notifications will be posted, as a result, your messages will be deprioritized."\[3\] (Firebase, *Set and manage Android message priority*.) Android 13 changed the accounting: "App Standby Buckets no longer determine how many high priority FCMs an app can use. System now downgrades the high priority messages if it detects an app consistently sending high-priority messages that don't result in a notification." (Android 13 behavior changes, all apps.)\[13\]

**C5 — The handler's execution window is short.** "Several seconds are given to process the message payload in the onMessageReceived handler, with slightly more time allocated for high priority messages."\[14\] The docs' sample splits work into "Handle message within 10 seconds" and, for anything longer, WorkManager.\[15\] Firebase adds: "There is a brief exemption for expedited jobs scheduled immediately after a high priority FCM onMessageReceived is dispatched."\[16\] (Firebase priority docs; Firebase blog, Apr 2025.)

**C6 — Android 14 requires a declared foreground service type, and each type has rules** (Android Developers, *Foreground service types*):

| Type | Permission | Runtime prereq | Fit for a persistent LAN WebSocket |
|---|---|---|---|
| `dataSync` | `FOREGROUND_SERVICE_DATA_SYNC` | none | **Poor for (c).** When targeting 35+, Android Developers' *Foreground service timeouts* page says dataSync services may "run for a total of 6 hours in a 24-hour period", with the limit "shared by all of an app's foreground services of the specified type". After that `onTimeout()` fires and you have "a few seconds" to `stopSelf()` or get "A foreground service of type dataSync did not stop within its timeout". Can't be started from `BOOT_COMPLETED` (API 35+). The timer resets when the user brings the app to the foreground. OK for (b). |
| `shortService` | none beyond `FOREGROUND_SERVICE` | none | **Good for (b).** "About 3 minutes", counted from `startForeground()`. If the app is still eligible to start a foreground service, calling `startForeground()` again "extends the timeout by another 3 minutes". Not sticky, can't start other foreground services; missing the timeout means an ANR "even if it has other valid foreground services". Battery-optimization exemption doesn't lift the cap. |
| `remoteMessaging` | `FOREGROUND_SERVICE_REMOTE_MESSAGING` | none | Plausible. Officially "Transfer text messages from one device to another. Assists with continuity of a user's messaging tasks when they switch devices." No timeout.\[17\] |
| `specialUse` | `FOREGROUND_SERVICE_SPECIAL_USE` | none | **Recommended for (c)** for a sideloaded app: the honest catch-all, no timeout. Needs a `PROPERTY_SPECIAL_USE_FGS_SUBTYPE` explanation that Play would review — irrelevant over adb.\[17\] |
| `connectedDevice` | `FOREGROUND_SERVICE_CONNECTED_DEVICE` | needs e.g. `CHANGE_NETWORK_STATE`/`CHANGE_WIFI_STATE` declared | Misfit: meant for "interactions with external devices" (BT/NFC/USB/network-attached hardware).\[17\] It would technically pass the runtime check, but it's the wrong semantics. |
| `microphone` | `FOREGROUND_SERVICE_MICROPHONE` + `RECORD_AUDIO` | while-in-use | Only if live mode also captures voice. It **cannot** be started from the background, even with the FCM exemption.\[9\]\[17\] |

**C7 — The Play Console foreground-service declaration doesn't apply to you, but the OS still enforces the manifest and runtime rules.** Play requires foreground-service types to be declared in Console (Policy > App content).\[17\]\[18\] A sideloaded debug APK is never reviewed, but the OS still throws if the type or permission is missing or the prerequisites aren't met. If you ever publish, `specialUse` will get human review; `remoteMessaging` is the easier sell.

**C8 — Doze.** In Doze, "network access is suspended" and jobs, syncs and alarms are deferred to maintenance windows.\[7\] High-priority FCM can wake the device and allow "some limited processing (including very limited network access)".\[14\] Normal-priority messages are held until the device leaves Doze.\[5\]\[6\] Useful test commands are in §7.

**C9 — App Standby buckets.** Before Android 13, the bucket capped high-priority FCMs.\[19\] Since Android 13 it doesn't:\[20\] deprioritization is driven by whether messages produce notifications (C4). Buckets still throttle jobs, alarms and network access. The restricted bucket (API 31+) applies the heaviest limits, and on API 33+ the system can move an unused app there automatically. The docs warn that if the app "doesn't show a notification upon receiving a high-priority FCM message, the user can't interact with the app and thus promote it to the active bucket."\[21\] A foreground-service or activity process state overrides bucket limits while it lasts.

**C10 — Android 16 (all apps, regardless of target).** "Background jobs started from a foreground service now must adhere to their respective runtime quotas."\[22\] WorkManager's docs add: "Starting with Android 16, long running workers (which use foreground services) can exhaust your app's job quota. If this happens, you can try launching the foreground service directly instead of using WorkManager." User-initiated data transfer (UIDT) jobs "are exempt from the ordinary job quotas".\[23\]

**C11 — Android 17 background audio hardening (all apps on Android 17).** Audio playback, focus requests and volume changes from the background require "a visible activity or… a foreground service that is not of type SHORT_SERVICE." When *targeting* API 37, that foreground service must also have while-in-use capabilities, i.e. have been started while visible or from a user action.\[24\] **This directly affects `flutter_tts` speaking from the FCM background handler** on a Pixel running Android 17. Expect background speech to fail silently unless live mode (a UI-started foreground service) is running. Android Developers' *Behavior changes: Apps targeting Android 17* confirms that "Android 17 introduces the ACCESS_LOCAL_NETWORK runtime permission to protect users from unauthorized local network access", and the *Local network permission* page says it "is required only if your app targets Android 17 (SDK 37) or higher" (it belongs to the NEARBY_DEVICES group). That matters because your server is on the LAN.

**C12 — UIDT jobs aren't a fit.** "User initiated jobs must be scheduled while the application is visible to the user (or in one of the allowed conditions)".\[25\] They're built for large, user-requested transfers (API 34+, `RUN_USER_INITIATED_JOBS`, `setUserInitiated(true)`),\[25\]\[26\] not a push-triggered chat socket.

## 3. Option-by-option analysis

| | (a) Notify, reconnect on tap | (b) Short foreground service from FCM | (c) Long-lived "live mode" foreground service | (d1) Expedited WorkManager drain | (d2) FCM + HTTP only, no background socket |
|---|---|---|---|---|---|
| Android legality | Fully compliant; keeps FCM high priority healthy | Legal only inside C1–C3; downgraded messages mean an exception | Fully legal when started from the UI | Brief exemption after high-priority FCM (C5); quota-bound (C10) | Compliant |
| Reliability in Doze | High (high-priority FCM wakes the device; the fetch fits in the limited network access) | Medium: races the exemption window; Flutter engine startup latency | High on Pixel (foreground-service process state); verify with force-idle | Medium: jobs can be deferred or stopped; no socket semantics | High for single items |
| Latency to full traffic | Human-bound (tap) | ~seconds after the wake | Real time | Seconds, capped duration | N/A (one item per wake) |
| Battery | ≈ one wake + one HTTPS round-trip per ≤60 s | One wake + radio for ≤3 min | Continuous: process kept alive, radio woken by keepalives (tune §6) | Similar to (b) | Lowest |
| UX cost | None beyond notifications | A foreground-service notification flashes for ≤3 min | A permanent notification (dismissible on Android 13+, but the service keeps running) | None visible (Android 12+) | Loses "conversation continues" |
| Complexity | Low | High (priority check, native timing, fallback, `onTimeout`) | Medium (ownership protocol) | Medium (Kotlin or `workmanager` plugin; no socket reuse) | Lowest |
| Verdict | **Adopt** | Optional later | **Adopt as opt-in** | Only as (b)'s fallback | Already have; it is (a) without the tap |

What (b) would need to be done right: native Kotlin checks `remoteMessage.priority == RemoteMessage.PRIORITY_HIGH` and calls `startForegroundService()` *synchronously inside `onMessageReceived`*, before any Dart runs. With FlutterFire this is awkward, because the plugin ships its own `FirebaseMessagingService`. Taking over the `MESSAGING_EVENT` intent means replacing FlutterFire's receiver path, and you should verify that an app-declared service still forwards correctly. Community evidence: the Notifee/React Native issue #470 (headless JS, the closest analogue to a Flutter background isolate) hit "startForegroundService() not allowed due to mAllowStartForeground false". Gating on `priority == high` cut crashes "by 99.99%" (3,065 → 28 per week).\[27\] The remaining crashes were mostly on non-Pixel OEM devices running Android 12–14.\[27\]

## 5. Single-socket ownership and handover

**Invariant:** at most one live `/ws/queue` connection per (user, device). The client enforces it with an ownership rule, and the server makes it true regardless (supersede).

```
            ┌────────── live mode OFF ──────────┐        ┌────────── live mode ON ───────────┐
 UI isolate │ owns socket while resumed;        │        │ proxy: sendDataToTask(out)        │
            │ closes after 30 s in background   │        │ addTaskDataCallback(in)           │
            └───────────────────────────────────┘        └───────────────────────────────────┘
 FGS isolate            (not running)                    │ TaskHandler owns socket; reconnects│
 FCM isolate  fetch-1-over-HTTP + notify (never sockets) │ same (or skip if live socket up)   │
 Server       per (user,device) slot; new conn supersedes old with close 4001; resume from seq │
```

Handover is make-before-break. The server's supersede rule means the moment both sockets exist is harmless:

- **Turning live mode on:** UI → `startService`; the TaskHandler connects with `last_seq`. The server closes the UI's socket with 4001. The UI treats 4001 as "stop, don't reconnect" and switches to proxy mode.
- **Turning live mode off:** UI connects (superseding the service's socket), then stops the service. The service treats 4001 as terminal.
- Store `last_seq` in a file or `SharedPreferencesAsync`, not the cached legacy `SharedPreferences` singleton. Each isolate has its own cache, so values go stale across isolates. Either reload or use the async API.

### 5.1 Server (FastAPI) — supersede and resume

```python
# ws.py
from fastapi import FastAPI, WebSocket, WebSocketDisconnect, Query
import asyncio, itertools

app = FastAPI()
slots: dict[tuple[str, str], WebSocket] = {}           # (user, device) -> ws
seq = itertools.count(1)
backlog: dict[str, list[tuple[int, dict]]] = {}        # user -> [(seq, msg)] (use your DB)

@app.websocket("/ws/queue")
async def ws_queue(ws: WebSocket, ticket: str = Query(...), device: str = Query(...),
                   last_seq: int = Query(0)):
    user = verify_ws_ticket(ticket)                     # short-lived, single-use
    await ws.accept()
    key = (user, device)
    if (old := slots.get(key)) is not None:
        try: await old.close(code=4001, reason="superseded")
        except RuntimeError: pass
    slots[key] = ws
    for s, msg in backlog.get(user, []):               # drain what was missed
        if s > last_seq: await ws.send_json({"seq": s, **msg})
    try:
        while True:
            m = await ws.receive_json()                 # client acks / agent traffic
            if m.get("type") == "ack": trim_backlog(user, m["seq"])
            else: await handle_client(user, m)
    except WebSocketDisconnect:
        pass
    finally:
        if slots.get(key) is ws: del slots[key]         # don't evict the successor

def has_live_mobile_ws(user: str) -> bool:
    return any(u == user for (u, _d) in slots)
```

Run uvicorn with protocol pings so dead Wi-Fi peers are detected server-side: `uvicorn app:app --ws-ping-interval 25 --ws-ping-timeout 20`.

### 5.4 UI isolate — owner when live mode is off, proxy when on

```dart
class QueueLink with WidgetsBindingObserver {
  WebSocket? _ws; bool _proxy = false; Timer? _idle;
  Future<void> start() async {
    WidgetsBinding.instance.addObserver(this);
    FlutterForegroundTask.addTaskDataCallback(_fromService);
    _proxy = await FlutterForegroundTask.isRunningService;
    if (_proxy) { FlutterForegroundTask.sendDataToTask({'op': 'hello'}); } // health check
    else { await _connect(); }
  }
  Future<void> _connect() async {
    final t = await AuthStore.wsTicket();
    final last = await SeqStore.read();
    _ws = await WebSocket.connect(
        'ws://lupin.lan:8000/ws/queue?ticket=$t&device=${Device.id}&last_seq=$last');
    _ws!.pingInterval = const Duration(seconds: 25);
    _ws!.listen(_onMsg, onDone: () async {
      if (_ws?.closeCode == 4001) { _proxy = true; return; } // superseded by service
      await Future.delayed(Backoff.next()); if (!_proxy) _connect();
    });
    await FirebaseMessaging.instance.getToken().then(Api.registerToken); // on every reconnect
  }
  void send(Map m) => _proxy
      ? FlutterForegroundTask.sendDataToTask(m)
      : _ws?.add(jsonEncode(m));
  void _fromService(Object d) => _onMsg(d is String ? d : jsonEncode(d));
  void _onMsg(dynamic raw) { final m = jsonDecode(raw); SeqStore.write(m['seq']); ui.add(m); }

  @override
  void didChangeAppLifecycleState(AppLifecycleState s) {
    if (_proxy) return;
    if (s == AppLifecycleState.paused) {
      _idle = Timer(const Duration(seconds: 30), () => _ws?.close(1000)); // "go quiet"
    } else if (s == AppLifecycleState.resumed) {
      _idle?.cancel(); if (_ws == null || _ws!.closeCode != null) _connect();
    }
  }
}
```

### 5.5 Live-mode service (flutter_foreground_task ≥ 9.2)

```dart
void main() { FlutterForegroundTask.initCommunicationPort(); runApp(const App()); }

Future<void> startLiveMode() async {          // call ONLY from visible UI (tap)
  FlutterForegroundTask.init(
    androidNotificationOptions: AndroidNotificationOptions(
        channelId: 'live', channelName: 'Live mode',
        channelImportance: NotificationChannelImportance.LOW),
    iosNotificationOptions: const IOSNotificationOptions(),
    foregroundTaskOptions: ForegroundTaskOptions(
        eventAction: ForegroundTaskEventAction.repeat(60000),
        allowWakeLock: true, allowWifiLock: true, autoRunOnBoot: false));
  await FlutterForegroundTask.startService(
      serviceId: 42, notificationTitle: 'Lupin live', notificationText: 'Connected',
      serviceTypes: [ForegroundServiceTypes.specialUse], // check enum name in your version
      callback: liveCallback);
}

@pragma('vm:entry-point')
void liveCallback() => FlutterForegroundTask.setTaskHandler(LiveHandler());

class LiveHandler extends TaskHandler {
  WebSocket? _ws; bool _stopping = false;
  @override
  Future<void> onStart(DateTime t, TaskStarter s) => _connect();
  Future<void> _connect() async {
    try {
      final tk = await AuthStore.wsTicket();                 // own HTTP; no main-isolate services
      _ws = await WebSocket.connect('ws://lupin.lan:8000/ws/queue'
          '?ticket=$tk&device=${Device.id}&last_seq=${await SeqStore.read()}');
      _ws!.pingInterval = const Duration(seconds: 25);
      _ws!.listen((m) { FlutterForegroundTask.sendDataToMain(m); _maybeNotify(m); },
          onDone: () async {
            if (_stopping || _ws?.closeCode == 4001) return;
            await Future.delayed(Backoff.next()); _connect();
          });
    } catch (_) { await Future.delayed(Backoff.next()); if (!_stopping) _connect(); }
  }
  @override
  void onReceiveData(Object d) {
    final m = d as Map;
    if (m['op'] == 'hello') { FlutterForegroundTask.sendDataToMain({'op': 'alive'}); return; }
    _ws?.add(jsonEncode(m));
  }
  @override
  void onRepeatEvent(DateTime t) {                          // watchdog: Doze exit, network change
    if (_ws == null || _ws!.closeCode != null) _connect();
  }
  @override
  Future<void> onDestroy(DateTime t, bool isTimeout) async { _stopping = true; await _ws?.close(1000); }
}
```

**Auth from any background isolate:** keep a long-lived refresh credential in storage that every isolate can read. Each isolate exchanges it over HTTP for a **short-lived, single-use WS ticket**. Never pass a live socket or an in-memory token between isolates; `IsolateNameServer`/`SendPort` carries only messages. The service isolate is a separate Flutter engine with its own plugin registration. Pure-Dart `dart:io` WebSocket and HTTP need no plugins there.

**Keepalive under Doze and Wi-Fi:** Dart `pingInterval` behaves as documented: if a pong isn't received within the interval, the socket is closed with `goingAway`.\[35\] The catch is that timers don't run while the CPU is suspended. A contributor's comment on signalapp/libsignal-service-java PR #45 (not an official Signal team write-up) described exactly this failure: a keepalive thread sleeping across screen-off "will wake up 50 seconds after you've picked up the device again and turned the screen on", by which time the socket was stale. So:

- Let the **server** drive pings (uvicorn `--ws-ping-interval`), and treat the client's ping as a liveness check.
- Hold a Wi-Fi lock and partial wakelock *only* in live mode.
- Rely on the watchdog `onRepeatEvent` to reconnect after Doze exit.

## 6. What the community reports: bugs, gotchas, workarounds, best practices, anti-patterns

**Consensus (strong):**

- **Always show a notification for every high-priority push.** Google's own guidance, the Android 13 change log, and field reports agree: otherwise you get downgraded, and a downgraded message can't start a foreground service (C2, C4).\[13\] Fleetbase's issue #268, fixed by PR #273, shows the flip side: without `android.priority=high`, pushes were missed "After ~30–60 min locked and stationary (deep Doze)" and delivered "only once the phone was unlocked or charged", while "The same message with android.priority = high was delivered immediately."
- **Check the delivered priority before starting a foreground service from a push.** In the Notifee #470 thread the maintainer added `priority`/`originalPriority` specifically "so you could only start the service conditionally on priority *still* being 'high'".\[27\] The Dart `RemoteMessage` in the firebase_messaging versions I reviewed doesn't expose delivered priority. That is one more reason (b) belongs in native code; check your exact version.
- **Don't do long work in `onMessageReceived`.** Hand anything over a few seconds to WorkManager (Firebase docs).\[36\]
- **Implement `onTimeout`/`onDestroy(isTimeout)`** for `dataSync` and `shortService`. Unhandled timeouts become `ForegroundServiceDidNotStopInTimeException` or an ANR. These crashes are widely reported on B4X and in Home Assistant's issue #5338 on the 6-hour limit.\[37\]\[38\]
- **Emulators and Pixels don't reproduce OEM killers.** A Pixel is the *benign* case (dontkillmyapp's framing; the Capacitor/DEV write-up says "the emulator and Pixel don't reproduce OEM restrictions").\[39\] Pixel Adaptive Battery still learns usage and restricts rarely used apps.\[40\] For live mode, set the app to "Unrestricted" (Settings → Apps → Lupin → App battery usage).\[41\]

**Bugs and gotchas:**

- **Force stop ≠ swipe away.** After a force-quit from Settings (and `adb shell am force-stop`), FCM isn't delivered until the app is reopened (FlutterFire docs).\[34\] Use swipe-away or `am kill` to simulate "killed".
- **Delayed handler in Doze** (flutterfire #4718, 2021, older plugin): the receiver logged `broadcast received` on time, but the Dart background handler only ran after `deviceidle unforce`.\[42\] It's probably fixed, but it's the reason to verify handler timing under `force-idle` yourself.
- **Debug builds are slower to spin up a background engine** (JIT). If you try (b), time the exemption race on `--profile`/`--release` builds.
- **flutter_foreground_task "zombie service":** the OS reports the service running while the `TaskHandler` never attached (reported when started while the UI was TOP).\[28\] Workaround: the `hello`/`alive` health check shown in §5.4, and restart on timeout.
- **flutter_background_service wakelock drain on Android 15** (#505) and "tasks don't execute on 15" (#502):\[29\]\[30\] unresolved, so avoid it.
- **Firebase + FOREGROUND_SERVICE declarations:** firebase-android-sdk #6960 reports a Play rejection where reviewers flagged `FirebaseMessagingService`.\[43\] It only matters if you publish; it's a reminder that declaring foreground-service permissions invites policy scrutiny.
- **Android 17 TTS from background** (C11): the existing "speak it if settings allow" step in the FCM isolate will stop working on Android 17 without a qualifying foreground service. Either speak only in live mode or on tap, or make the notification sound the audible cue.
- **`SharedPreferences` across isolates:** each isolate caches its own copy. Use `SharedPreferencesAsync` or `reload()` for `last_seq`/tokens.

**Anti-patterns:**

- Sending data-only high-priority messages that sometimes produce no notification ("silent sync"). FCM will learn the pattern and downgrade you.\[16\]
- Keeping a socket in the plain background "because it seems to work": it dies at the first Doze entry. Community threads (MIT App Inventor, Qt forum) keep finding the same thing: only a foreground service holds up.\[44\]\[45\]
- Choosing `dataSync` for an always-on connection on API 35+: the 6 h/24 h cap bites without warning in hour 7.\[46\]
- Two sockets "temporarily" (UI and service) without server-side supersede: duplicate delivery, and acks that fight over `last_seq`.
- Reconnecting in a tight loop on `onDone` without backoff (battery, and server log floods), or reconnecting on close code 4001.
- Using `connectedDevice` or `systemExempted` to dodge rules. `systemExempted` throws `ForegroundServiceTypeNotAllowedException` for normal apps.\[17\]

**Where opinion is split:**

- **`remoteMessaging` vs `specialUse` for chat-like sockets:** no official ruling for "client ↔ own server". `remoteMessaging`'s description is about cross-device continuity, and `specialUse` is the catch-all.\[17\] For sideloading it makes no practical difference.
- **Whether a foreground service fully exempts network access from Doze:** the docs list foreground-service processes among the exemptions, and practitioners (Spreaker's audio team) found foreground services "exempted by both App Standby and Doze", apart from an old Android 6 bug.\[5\]\[47\] Treat it as true on Pixel and verify with `force-idle`.
- **Whether (b) is worth it:** RN/Notifee users got it mostly working with priority gating. Others saw residual failures on OEM devices.\[27\] On a Pixel with visible notifications it's plausible, but it's the least-tested path for Flutter specifically.

## 7. Incremental build and test sequence (emulator → phone)

Use an emulator image **with Google Play** (API 34 and API 35/36; add 37 if available), signed in to a Google account. Point the server at `10.0.2.2` from the emulator, or run the emulator on the same host as the LAN server.

**Step 0 — Baseline and tooling**
```bash
PKG=com.example.lupin_af
adb logcat -c && adb logcat -s FLTFireMsgReceiver ActivityManager flutter &
adb shell dumpsys deviceidle            # mState=ACTIVE
adb shell am get-standby-bucket $PKG
```

**Step 1 — (a+): unconditional notification + tap → reconnect**
- Make the fetch fail on purpose (stop the server): a fallback notification must still appear.
- Tap it: the app opens and the WS reconnects with `last_seq`, and the backlog drains.
```bash
adb shell input keyevent KEYCODE_HOME          # background
# or simulate "killed" without force-stop:
adb shell am kill $PKG                          # kills background process only
```

**Step 2 — Doze delivery**
```bash
adb shell dumpsys battery unplug
adb shell dumpsys deviceidle force-idle         # deep idle
adb shell dumpsys deviceidle get deep           # expect IDLE
# trigger a ws_wake from the server; expect notification within seconds
adb shell dumpsys deviceidle unforce && adb shell dumpsys battery reset
```
Pass: the notification appears *while* the device is IDLE, not only after `unforce`.

**Step 3 — Buckets**
```bash
for b in active working_set frequent rare restricted; do
  adb shell am set-standby-bucket $PKG $b; adb shell am get-standby-bucket $PKG
  # send ws_wake; record latency / delivery
done
adb shell am set-inactive $PKG true; adb shell am get-inactive $PKG
adb shell cmd appops set $PKG RUN_IN_BACKGROUND ignore   # harsh background restriction
adb shell cmd appops set $PKG RUN_IN_BACKGROUND allow
```

**Step 4 — Live mode (c) on/off with handover**
```bash
adb shell dumpsys activity services $PKG | grep -iE "ForegroundService|isForeground|types"
```
- Toggle on from the UI: the server log shows a new connection and a 4001 close for the UI socket, and the UI shows proxy mode.
- Background the app, `force-idle`, wait 10 min, push server traffic: messages arrive while idle, and `dumpsys deviceidle` shows IDLE.
- Toggle off: the UI supersedes the service socket and the service stops. The server never shows two slots for the device.

**Step 5 — Battery sanity**
```bash
adb shell dumpsys batterystats --reset
# 1 h screen-off in live mode, then:
adb shell dumpsys batterystats $PKG | grep -iE "wake|wifi|Foreground"
```
Compare against a live-mode-off hour. Tune server ping (25 → 60 s) and the watchdog interval.

**Step 6 — Optional (b), only after 1–5 pass**
Build a native `onMessageReceived` path: `if (priority == PRIORITY_HIGH) startForegroundService(shortService)`, else fall back to (a). Catch `ForegroundServiceStartNotAllowedException`. Stop within 3 min and implement `onTimeout`. Test on a `--profile` build under `force-idle`.

**Phone-only proofs (Pixel):**
- Real Doze entry: the device sits stationary, screen-off and unplugged for 30–60+ min. `force-idle` is an approximation; community gists note `step deep` alone doesn't reproduce real network cut-offs, while `force-idle` does.\[48\]
- Wi-Fi power-save behaviour and AP/NAT idle timeouts. The emulator's virtual NIC doesn't model them.
- Adaptive Battery learning, and deprioritization over days (FCM's pattern detection is server-side and statistical; an emulator session won't trigger it).
- Android 17 background-audio enforcement on real hardware, and Pixel-specific foreground-service notification UX (dismissal, Task Manager "Stop").

## 8. Failure-mode test matrix

| Failure mode | How to induce | Expected behaviour | Pass criterion |
|---|---|---|---|
| **FCM token rotation** | Debug button: `deleteToken()` then `getToken()`; or clear app data and log in | `onTokenRefresh` → register; server `UnregisteredError` → delete stale token | Next `ws_wake` reaches the new token; no sends to the stale one after the first 404 |
| **Server restart** | `kill -TERM` uvicorn, restart after 5/60 s | UI or service socket `onDone` → jittered backoff → reconnect with `last_seq`; backlog replayed once | No duplicates (dedupe by `seq`); reconnect ≤ backoff cap |
| **Network change** | `adb shell svc wifi disable` / `enable`; `adb shell cmd connectivity airplane-mode enable/disable`; on the phone, roam between APs | Socket errors → backoff; watchdog `onRepeatEvent` reconnects; server ping detects the half-open peer | Reconnect within one watchdog period after Wi-Fi returns |
| **Doze entry/exit** | `force-idle` → wait → `unforce`; on the phone, a real 1 h idle | (a): notification during IDLE. (c): socket survives or is re-established on the first watchdog tick after exit | No lost messages (the server backlog covers gaps) |
| **FCM deprioritization** | Deliberately skip `show()` for N pushes (test build), or revoke POST_NOTIFICATIONS | Over time, delivery shifts to normal priority and is delayed in Doze; (b) throws `ForegroundServiceStartNotAllowedException` | App code never skips the notification; if permission is revoked, a UI banner explains why live wakes degrade |
| **Notification permission denied** | `adb shell pm revoke $PKG android.permission.POST_NOTIFICATIONS` | Nothing can be posted → messages deprioritized (Firebase docs)\[3\] | Detect it at login; prompt the user; server-side, treat the device as "no push" |
| **Handler window overrun** | Server delays `/fetch-one` by 15 s | Timeout → fallback notification posted anyway | Notification always shown within ~5 s |
| **Force stop** | `adb shell am force-stop $PKG` | No FCM until the user opens the app (documented)\[34\] | Documented limitation; not a bug |
| **Two sockets fighting** | Toggle live mode rapidly; open the UI while the service reconnects | Server supersede (4001); losers don't reconnect | Server never holds >1 slot per device; `last_seq` is monotonic |
| **dataSync / shortService timeout** (if used) | Run >6 h `dataSync` (API 35+), or >3 min `shortService` | `onTimeout` → `stopSelf()`; fallback to (a) | No `DidNotStopInTime` exception or ANR |
| **Zombie TaskHandler** | Start live mode while the UI is TOP; kill the UI engine | `hello` → no `alive` within 3 s → UI restarts the service | Health check recovers without user action |
| **Android 17 background TTS** | Push while backgrounded, live mode off, on API 37 device/emulator | Speech suppressed; notification still shown | Speech only when UI visible or live mode on |
| **Standby bucket = restricted** | `am set-standby-bucket $PKG restricted` | High-priority FCM still delivered (bucket no longer caps high-priority FCM on API 33+); jobs throttled\[20\] | (a) still works; (b)'s WorkManager fallback may be deferred |
| **Reboot** | `adb reboot` | Live mode doesn't auto-start (`autoRunOnBoot: false`; several types are banned from `BOOT_COMPLETED` on API 35+); FCM works once the device is unlocked | User re-enables live mode; (a) works immediately |

## Caveats

- Google documents the FCM foreground-service exemption only as "brief". The 10 s figure is microG's implementation, not a confirmed Google value. Measure your own margin.
- Android Developers' *Local network permission* page confirms the `ACCESS_LOCAL_NETWORK` runtime permission "is required only if your app targets Android 17 (SDK 37) or higher"; request it before raising `targetSdk` to 37, since the server is on the LAN. Flutter's default `targetSdkVersion` depends on your Flutter SDK version.
- The claim that a foreground service exempts network access from Doze rests on the docs' exemption list plus practitioner reports. Validate it with Step 4 on the actual Pixel.
- API names in the `flutter_foreground_task` snippets follow the 9.x–11.x changelog (`serviceTypes`, `onDestroy(isTimeout)`, `sendDataToTask`/`sendDataToMain`, `TaskStarter`). Check the exact enum and parameter names against the version you pin, and read its migration doc when moving to 11.x (Flutter 3.44/Dart 3.12 minimum).\[1\]
