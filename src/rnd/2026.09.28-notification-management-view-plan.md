## 1. Settings model

All keys stay in `NotificationPreferences` (SharedPreferences) — readable from
the background isolate, which is the constraint that decides this.

| key | default | why that default |
|---|---|---|
| `notif.enabled` | `true` | master; today's behaviour |
| `notif.background.enabled` | *migrated* | see §4 |
| `notif.foreground.enabled` | `true` | today's behaviour |
| `notif.background.priority.{low,medium,high,urgent}` | all `true` | background shows every fetched item today — `showNotification` is unconditional |
| `notif.foreground.priority.low` | `false` | low is already silent in the foreground (`notification_audio_service.dart:88` early-returns; TTS `_isSpeakable` excludes it) |
| `notif.foreground.priority.{medium,high,urgent}` | `true` | today's behaviour |

The asymmetric `low` default is deliberate: **every default preserves what the
app does today**, so an install that never opens this view behaves identically.

One pure class, `NotificationDeliveryPolicy` (no Flutter import, so it is unit
-testable and isolate-safe):

```dart
bool allows( { required String surface, required String priority } )
bool anyAllowedOn( String surface )   // the pre-fetch gate, §2
```

Truth: `master && surfaceEnabled && priorityChecked`. Unknown priority ⇒ denied.

## 2. Gate points

**Background** — `FcmWakeChain.handleWake`, two gates, because the priority is
not knowable until after the fetch.

- **Gate A, pre-credentials** (exactly where Pocholo put his): `!anyAllowedOn( 'background' )` ⇒ total no-op. No radio, no fetch, no mark-played, queue intact.
- **Gate B, fetch the LIST, take the oldest ALLOWED item** (Tiffany's ruling,
  2026-09-28 21:15): a denied item is never consumed *and* never blocks the
  ones behind it. Only the item actually shown is marked played.

`GET /api/notifications/{user}?include_played=false&limit=N` already exists
(`notifications.py:2495`) and needs **no server change**. Three things verified
in the source before relying on it:

- It is a **pure read** — serving it marks nothing played, same as `/next`.
- Same auth (`require_api_key_or_jwt` + `require_path_identity_owner`) and same
  path param as `/next`, which mobile already calls with the email, so the
  identical value works.
- WARNING: **its docstring says "sorted by timestamp (newest first)" and the
  handler does no sorting at all** (`notifications.py:2536`). It walks
  `queue_list` in the same order `get_next_unplayed` does, so it returns queue
  order and `/next` is simply its first element. Oldest-allowed is therefore the
  **first** match, not the last. I am coding to the handler, not the docstring,
  and the test pins the order so a later server fix cannot flip it silently.

The chain's `fetchNextNotification` seam becomes `fetchUnplayed( email, token )`
returning a list; the chain takes the first allowed entry and leaves the rest
untouched. One shown, one marked played, everything else still waiting.

**Foreground** — `NotificationBloc._onExternalUpdate` (`notification_bloc.dart:240`),
one gate in front of the `_audio?.handleIncoming` / `_tts?.enqueueIfSpeakable`
pair. `_refreshCurrent( emit )` still runs: the list still updates, nothing is
consumed, the ding and the speech are what's suppressed.
