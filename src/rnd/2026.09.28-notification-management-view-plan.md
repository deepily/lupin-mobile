## 1. Settings model

All keys stay in `NotificationPreferences` (SharedPreferences) — readable from
the background isolate, which is the constraint that decides this.

| key | default | why that default |
|---|---|---|
| `notif.enabled` | `true` | master; today's behaviour |
| `notif.background.enabled` | *migrated* | see §4 |
| `notif.foreground.enabled` | `true` | today's behaviour |
| `notif.background.priority.{low,medium,high,urgent}` | all `true` | background shows every fetched item today — `showNotification` is unconditional |
| `notif.foreground.priority.low` | `false` | low is already silent in the foreground (`notification_audio_service.dart:88` early-returns; TTS `_isSpeakable` excludes it) |
| `notif.foreground.priority.{medium,high,urgent}` | `true` | today's behaviour |

The asymmetric `low` default is deliberate: **every default preserves what the
app does today**, so an install that never opens this view behaves identically.

One pure class, `NotificationDeliveryPolicy` (no Flutter import, so it is unit
-testable and isolate-safe):

```dart
bool allows( { required String surface, required String priority } )
bool anyAllowedOn( String surface )   // the pre-fetch gate, §2
```

Truth: `master && surfaceEnabled && priorityChecked`. Unknown priority ⇒ denied.

## 2. Gate points

**Background** — `FcmWakeChain.handleWake`, two gates, because the priority is
not knowable until after the fetch.

- **Gate A, pre-credentials** (exactly where Pocholo put his): `!anyAllowedOn( 'background' )` ⇒ total no-op. No radio, no fetch, no mark-played, queue intact.
- **Gate B, fetch the LIST, take the oldest ALLOWED item** (Tiffany's ruling,
  2026-09-28 21:15): a denied item is never consumed *and* never blocks the
  ones behind it. Only the item actually shown is marked played.

`GET /api/notifications/{user}?include_played=false&limit=N` already exists
(`notifications.py:2495`) and needs **no server change**. Three things verified
in the source before relying on it:

- It is a **pure read** — serving it marks nothing played, same as `/next`.
- Same auth (`require_api_key_or_jwt` + `require_path_identity_owner`) and same
  path param as `/next`, which mobile already calls with the email, so the
  identical value works.
- WARNING: **its docstring says "sorted by timestamp (newest first)" and the
  handler does no sorting at all** (`notifications.py:2536`). It walks
  `queue_list` in the same order `get_next_unplayed` does, so it returns queue
  order and `/next` is simply its first element. Oldest-allowed is therefore the
  **first** match, not the last. I am coding to the handler, not the docstring,
  and the test pins the order so a later server fix cannot flip it silently.

The chain's `fetchNextNotification` seam becomes `fetchUnplayed( email, token )`
returning a list; the chain takes the first allowed entry and leaves the rest
untouched. One shown, one marked played, everything else still waiting.

**Foreground** — `NotificationBloc._onExternalUpdate` (`notification_bloc.dart:240`),
one gate in front of the `_audio?.handleIncoming` / `_tts?.enqueueIfSpeakable`
pair. `_refreshCurrent( emit )` still runs: the list still updates, nothing is
consumed, the ding and the speech are what's suppressed.

## 7. Phase 2 — mute by sender, and quiet hours (2026.09.29)

*Added by Tiffany. Rick, by voice on 2026-09-29: the phone he keeps for managing
Lupin from a distance is "driving me crazy". He picked mute by sender and quiet
hours, built on this view, with mute modelled on the web clients. Row
`f1e80e67`.*

### 7.1 What the web clients actually do (and why we don't copy it exactly)

Neither web client has a mute. The nearest thing is the **per-session
speakerphone flag** (🔊/🤭):

- It is stored in the session's bridge file on the server and toggled with
  `POST /api/cosa-voice/speakerphone/{session_id}`, body `{"on": bool}`
  (`cosa/rest/routers/speakerphone.py`).
- It is keyed by **session id**, so it ends when the session does. A persona
  that re-spins comes back loud.
- It **demotes** instead of silencing: the legacy client rewrites high and
  urgent to medium, which means a ding and no speech
  (`notifications.js:6647-6666`), and urgent is demoted like everything else.
  The multiplexer uses the flag only for pinning and icons.
- Nothing like quiet hours exists anywhere in the server or the clients.

That flag solves a different problem: a session talking too much while you are
at the desk. The phone's problem is **who is allowed to reach me at all**, and
the answer has to survive re-spins. So we borrow the idea and change the key.

### 7.2 Settings model (additions)

All values are stored in `NotificationPreferences`, which the background
process can read, as in §1.

| key | default | meaning |
|---|---|---|
| `notif.muted.senders` | `[]` | muted sender keys (see 7.3) |
| `notif.muted.urgentBypass` | `true` | an urgent from a muted sender still gets through |
| `notif.quiet.enabled` | `false` | quiet hours on |
| `notif.quiet.start` / `notif.quiet.end` | `22:00` / `07:00` | local time; the window may cross midnight |
| `notif.quiet.urgentBypass` | `true` | an urgent still gets through during quiet hours |

Every default leaves current behaviour unchanged, which is the same rule as §1.

### 7.3 The sender key

**Persona name when the server stamped one** (`voice_persona.name`, lowercased
and with accents removed, e.g. `maya`), **otherwise the raw `sender_id`**. The
persona name survives a re-spin, but the session id does not, and "mute Maya"
has to still mean Maya an hour later. The label shown is the same
`notificationSenderLabel()` the notification shade uses, so the screen says
"🌻 Maya" exactly as the notification does.

### 7.4 The gate

`NotificationDeliveryPolicy.allows()` gets two more inputs, `senderKey` and
`now` (the clock is passed in so the function stays pure and testable):

```
allows = master && surface && priority
         && !( muted(sender)  && !(urgent && muteBypass) )
         && !( inQuiet(now)   && !(urgent && quietBypass) )
```

The existing surface and priority switches are applied first, so urgent can
still be switched off entirely. Both call sites already have the payload in
hand:

- the background wake chain (`fcm_bootstrap.dart:561`, the "oldest allowed
  item" of §2)
- the foreground bloc (`notification_bloc.dart:258`)

**It suppresses, never deletes, the same as §2.** A muted item stays unplayed
on the server and is in the list when the app is opened.

`anyAllowedOn()` stays priority-only. Sender is unknowable before the fetch,
and quiet hours only rule out a fetch when both bypasses are off, which is an
edge case not worth the extra branch.
