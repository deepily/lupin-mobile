## 5. Three traps that will cost the next seat an evening each

1. **`await bloc.close()` inside a `testWidgets` body never returns** for any bloc with at least one
   `on<Event>` handler. `close()` waits on handler-subscription cancellation, which completes only on the real
   event loop; the fake-async zone never turns while the body is parked. Fix: `await tester.runAsync( () => bloc.close() )`.
2. **Two bloc handlers awaiting Dio in one fake-async turn never complete.** It presents as *"the Dart compiler
   exited unexpectedly"*, which points nowhere near the cause. Fix: `runAsync` **then** `pumpAndSettle` — Dio
   also schedules a zero-duration `Timer` inside the fake zone that one `pump()` never drains. `pumpAndSettle`
   is only safe where there is no spinner. **The root cause below that statement is not established** — do not
   repeat it as if it were.
3. **`addTearDown( bloc.close )` deadlocks if a handler is still in flight.** María's form is right and
   mutation-proved, but it is not unconditionally safe.

⚠️ And the naming trap: the class is **`FinishedTasksScreen`**, while its test file is
`finished_tasks_pane_test.dart`. That mismatch is what made me name a non-existent `FinishedTasksPane` in a
write-up earlier today (corrected in `9fb33e6`).

## 7. The widget-test audit he asked for, and what it found

**Question asked**: *"have you fully implemented widget level testing for all of this new functionality?"*
**Honest answer**: it was broad but **not complete — two seams had no test at all**, and both are the same
defect family this feature has already been bitten by twice. I enumerated rather than recalled.

### What was already covered
`test/widget/` holds 66 files. The Broadcast work has `broadcast_pane_test.dart` plus four unit files
(`bloc`, `models`, `repository`, `listening_watch`), and the other four surfaces each have pane/screen widget
tests plus bloc, model and repository units. The reachability guard `fleet_panes_reachable_test.dart` covers
all five doors and their tappability.

### 🔴 Gap 1 — `PaneHostScreen` had **zero** tests of any kind
Referenced only by its own file and `home_screen.dart` — the exact orphan shape I found for the panes, but
this time for the **wrapper two of the five surfaces depend on**. Its header states three contracts and
nothing checked any of them. The load-bearing one: **the bloc's lifetime is the route's**, which is why
`blocFactory` is a factory and not an instance. Pass an instance instead, or hoist the provider above the
route, and every pane test stays green while a closed pane keeps polling the server.

⇒ **Written**: `test/widget/fleet/pane_host_screen_test.dart` — Scaffold/AppBar, bloc actually provided and
drivable by a tap, factory called exactly once across rebuilds, and **the bloc is closed when the route is
popped** (with the unopened-pane case asserted too: no route, no bloc, no requests).

### 🔴 Gap 2 — the ack **dispatch** seam had no test
`app.dart:132-137` is the only path from a socket frame to `BroadcastAckReceived`. Every existing broadcast
test **dispatches that event by hand** — the bloc test proves the folding, the models test proves the parse,
the pane test proves the render, and **none of them touches the wire**. Delete that arm from `app.dart` and
all of them stay green while the pane renders a fleet that looks like it ignored the operator.

⇒ **Written**: `test/service_integration/broadcast_ack_dispatch_test.dart` — the real `WsBlocDispatcher`, the
real `BroadcastBloc`, the real parse, and the frame shape the server actually pushes (**`message` is an empty
string by design**; everything identifying is in `payload`). Five cases: one frame raises the tally, a
redelivery does not inflate it, an ack for another broadcast is ignored, an ordinary notification folds
nothing, and a malformed ack is dropped rather than fatal.

⚠️ Placed in `service_integration/` rather than `widget/` on purpose — it drives the dispatcher, not a widget
tree, and `single_dispatcher_test.dart` is the established precedent for exactly this shape. Calling it a
widget test would have been the more flattering filing and the less accurate one.

### Both new files are green, and both are **proved able to fail**

A guard nothing can fire is not a guard — this feature has been bitten by that twice, so neither file is
offered on the strength of passing alone.

| File | Result | Mutation | Killed |
|---|---|---|---|
| `test/widget/fleet/pane_host_screen_test.dart` | **4/4 pass**, 2s | `BlocProvider( create: )` → `BlocProvider.value( blocFactory( context ) )` — i.e. the provider stops owning closure | **the lifetime test, and only it** (3 +, 1 −) |
| `test/service_integration/broadcast_ack_dispatch_test.dart` | **5/5 pass**, 2s | the broadcast arm in `app.dart` disabled | **both positive cases** (3 +, 2 −) |

⚠️ **The three survivors of mutation A are the negative cases, and they were always going to survive.** They
assert that nothing folds on an unrelated, duplicate or malformed frame — disabling the arm also produces
nothing folded, so they cannot distinguish the two. Reporting them as "survived" without that sentence would
make the file look weaker than it is; reporting only the 2 kills would make it look stronger. Both production
files were reverted with `git checkout HEAD --` and verified **byte-identical**.

⚠️ **The first test hung, and it was my own documented trap.** `addTearDown( cubit.close )` on an instance the
`BlocProvider` also closes is a second close, and it deadlocks inside a `testWidgets` body — the run sat at
`+0` for five minutes. Cause established by elimination, not guessed: removing the teardown made it 4/4 in two
seconds. The file now carries that note where the next seat will read it.

⚠️ **And a second self-inflicted one worth recording**: I started two `flutter test` runs concurrently in the
same tree, which share one `.dart_tool/` build cache, and both stalled at zero bytes. I then read their
`exit 0` as a result when in fact I had killed them. **A kill that reports success is indistinguishable from a
pass if you only read the exit code.**
