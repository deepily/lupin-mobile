# Android toolchain: a briefing for someone arriving cold

Date: 2026-09-15 · Author: Tiffany 💍 · For: an outside expert with no context on this project
Status: **open question — we want your opinion before we spend more time**

---

## What we want from you

**One question, at the bottom of this page:** we think the answer is "install a separate JDK 21 and move on," and we would like to know whether you would do something else instead. Everything above the question is the evidence, laid out so you do not have to take our word for anything.

We are not asking you to review code. We are asking whether we have painted ourselves into a corner we cannot see, because everyone who has looked at this so far has been inside it.

## The project, in four sentences

Lupin Mobile is a Flutter app — an Android voice client that records a question, ships it to a FastAPI backend, and plays back the answer. It is a prototype, roughly six months old, with about 1,100 passing tests and no users other than its author. It lives as a standalone repo that is also a subtree of a larger project. Nothing about it is shipped, published, or depended on by anyone.

That last sentence matters for your advice: **we can afford disruptive fixes.** There is no release train to protect.

## The symptom

The author's laptop cannot build the app. Gradle prints a bare `25.0.3` as the entire error, with Java restricted-method warnings above it.

## What we established

### The version stack, as measured tonight

| Layer | Laptop (macOS 15.7.7, Apple Silicon) | This repo pins | Desktop (Linux, where the agents run) |
|---|---|---|---|
| Flutter | **3.35.1**, at `~/flutter/v3.35.1` | **3.32.0**, vendored at `<repo>/flutter` | 3.32.0 vendored |
| Dart | 3.9.0 | 3.8.0 | 3.8.0 |
| JDK in use | **25.0.3** | — | **11.0.19** |
| Where that JDK comes from | Android Studio 2026.1's bundled JBR | — | system default |
| Android SDK | 36.0.0, build-tools 36.0.0 | — | **none installed** |
| Gradle | 8.12 | 8.12 | 8.12 |
| AGP | 8.7.3 | 8.7.3 | 8.7.3 |

### The three facts that constrain everything

1. **Gradle 8.12 tops out at JDK 23.** Java 24 needs Gradle 8.14; Java 25 needs Gradle 9.1.0. ([Gradle compatibility matrix](https://docs.gradle.org/current/userguide/compatibility.html))
2. **AGP has never supported JDK 25.** AGP 9.4.0 — the current release as of this month — still lists JDK 17 as minimum and default. There is no JDK 25 row in that table at all. `flutter/flutter#187223`, "Java 25 Support in Flutter Android Builds", has been open since 2026-05-28 and its own suggested workaround is "use JDK 17 or 21."
3. **Flutter 3.32's tooling caps Gradle at 8.12 and AGP at 8.7.3** — exactly our pins — in `flutter_tools/lib/src/android/gradle_utils.dart`. So on 3.32 there is no Gradle 9 to move to without moving Flutter first.

### The thing we got wrong, and how

The author proposed: *"Android Studio bundles JBR 21 — can we just point at that?"* Our own research document said the same thing, citing the Ladybug release.

**It is stale.** His `flutter doctor -v` shows Android Studio **2026.1** bundling **JBR 25.0.3** — so the bundled JBR *is* the Java breaking the build. Flutter is picking it up exactly as designed; our working theory that "Studio was not detected" was simply wrong.

We record this because it is the kind of error that survives review: a true statement about one version, cited correctly, that quietly stopped being true.

### What we verified by doing, not reasoning

On the Linux desktop, a worker installed Temurin 21, ran `flutter config --jdk-dir`, assembled an Android SDK, and **built a debug APK successfully, twice** — 208 MB, correct package id, all four ABIs, verified with `aapt2 dump badging`.

**But be clear about what that does and does not prove.** The desktop failed from *below* the floor (JDK 11 against AGP's minimum of 17). The laptop fails from *above* the ceiling (JDK 25 against Gradle's maximum of 23). Both land inside the supported window, so the inference is strong — **but the laptop's specific failure was never reproduced.** We are telling you this rather than letting you assume we reproduced it.

### The version-skew question — since answered, and it changes nothing

This section asked an open question when first written. We have since answered it ourselves, and we are leaving the answer here rather than the question, because handing you something we already resolved would waste the one thing we are asking you for.

**Which Flutter builds this repo on the laptop: his 3.35.1. The vendored 3.32.0 is never even copied there.** Three independent mechanisms, each sufficient on its own:

- `src/scripts/build-and-deploy-lupin-mobile.sh` calls bare `flutter`, so `PATH` resolves it to `~/flutter/v3.35.1`. It never calls `./flutter.sh`.
- `flutter build` **rewrites** `flutter.sdk` in `android/local.properties` from `Cache.flutterRoot` (`gradle_utils.dart:751`). That file does not pin the SDK — it is a generated cache of whichever SDK last built. It is tracked in git, which is why it churns.
- `src/scripts/rsync-lupin-mobile.sh` excludes `flutter/` outright.

**And 3.35.1's caps, read from that tag's own `gradle_utils.dart`:**

| Constant | 3.32.0 | 3.35.1 | Moved? |
|---|---|---|---|
| `maxKnownAndSupportedGradleVersion` | 8.12 | **8.12** | no |
| `maxKnownAndSupportedAgpVersion` | 8.7.3 | 8.9.1 | yes |
| `oneMajorVersionHigherJavaVersion` | 24 | 24 | no |
| top `_javaGradleCompatList` row | javaMin 23 · javaMax 24 (exclusive) | identical | no |

**3.35.1 gets zero steps closer to JDK 25.** The Gradle cap is the binding constraint and it did not move. Only the AGP cap rose — a different axis that does nothing for Java. No path opens.

**The skew is mild rather than blocking**: the repo's pins sit inside 3.35.1's caps, so it builds this repo as-is with no migration prompt. Three loose ends we noted: `pubspec.lock` is gitignored, so the two machines resolve dependencies independently (Dart 3.9.0 against 3.8.0); the tracked `.metadata` still records 3.32.0's revision, so `flutter migrate` must not be run from the laptop; and `android/local.properties` is tracked and rewritten on every build.

So the skew is real, it is invisible day to day, and it is **not** why the build fails.

## The options as we see them

| # | Option | Cost | What we think |
|---|---|---|---|
| **A** | Install Temurin 21 separately, `flutter config --jdk-dir`. No repo change; user-level config; undo is one command | ~15 min plus a slow first build | **Our recommendation.** Verified end-to-end on another machine |
| **B** | Upgrade Flutter past 3.32 to lift the Gradle cap, then move Gradle and AGP | Days. New Gradle, new AGP, the built-in-Kotlin migration, ~8 pub dependencies | Ends on a JDK that AGP still does not list. A Flutter upgrade wearing a Gradle costume |
| **C** | Align the repo's pinned Flutter with the 3.35.1 the author already runs | Modest: update `.metadata`, decide whether to keep vendoring at all, settle `pubspec.lock` | Does **not** fix the build — 3.35.1's Gradle cap is identical. It is hygiene, and it is where we would most like your view on timing |
| **D** | Do nothing; the laptop build is not currently blocking any shipped work | Free | Leaves the repo unbuildable on every machine we have, which will bite at the worst moment |

---

## The question

Option A is now the only path that reaches a working build — B and C both dead-end at the same Gradle cap. So the question is not "which fix" but whether we should trust the one we have:

**Is there a reason to distrust option A that we cannot see from inside?** We have one verified build on a different machine failing in the opposite direction, and one unreproduced failure on the machine that matters. We are aware that is not the same as knowing, and we would rather hear it from you than discover it.

Second, and this is the one where an outside eye is genuinely worth more than ours: **a repo that vendors its own Flutter while the developer drives a different one on `PATH`, with `local.properties` tracked in git and rewritten by every build** — is that a latent problem worth paying down now, or is it normal enough to leave alone for a prototype? We have been living inside this arrangement long enough to have stopped noticing it.

Third, optional: the build requests an 8 GB Java heap and pulls ~2.7 GB of SDK on first run, and eighteen plugins disagree with the project about the NDK version — all of which we currently treat as noise because the APK builds anyway. **Are we wrong to treat any of that as noise?**
