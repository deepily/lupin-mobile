## 1. 🔴 Fleet Status: the perpetual spinner — B1

**His report**: spinner forever, nothing rendered, and **no console output after the arbiter fleet-size-cap
request, which succeeded.** "Dead in the water."

**What I found — a silent-failure path that can produce exactly that, in `fleet_status_bloc.dart:137-169`:**

The spinner branch is `composite == null && error == null` (`fleet_status_screen.dart:103`). So a permanent
spinner means **neither** `FleetStatusLoaded` **nor** `FleetStatusFailed` was ever added. There is one path
that does that:

1. `fetchState()` succeeds.
2. `fetchSizeCap()` is cancelled → `fleet_repository.dart:83` **rethrows** the `DioException`.
3. The inner catch only handles `FleetApiException`, so the rethrow passes straight through it.
4. The outer `on DioException` does `if ( e.type == cancel ) return;` — **returns, adding nothing.**
5. `composite` stays null, `error` stays null. Spinner.

The token is cancelled by `_stopTimerAndRequest()`, which fires on `onPaneHidden()` or any non-`resumed`
lifecycle event — and Android delivers `inactive` routinely during a route transition, which is precisely when
this pane is opening.

### 🔴 SECOND REVISION — María checked my "nothing retries" claim and it was FALSE

I wrote *"the mixin cancelled the timer at the same moment, so nothing retries."* **That is wrong, and I had
the correct analysis before I wrote the sentence.** Measured at `pane_polling_mixin.dart:96-107`:

`inactive` → `_appForeground = false` → `_reconcile()` stops the timer and cancels the request. Then `resumed`
→ `wasForeground` is `false` → `_reconcile( refreshNow: !wasForeground )` → **`refreshNow: true` → `_fire()`.**
**It does refresh on the way back.**

⇒ **This materially weakens my own diagnosis, so the plan has to say so.** If the cancel came from a lifecycle
blip, the pane **self-heals on the next resume** — which means a *permanent* spinner is probably **not** this
path. And on a live pane nothing else cancels: `_stopTimerAndRequest` only runs when `_paneVisible` is false
(dispose only) or `_appForeground` is false (a lifecycle event, which recovers).

⇒ **So I no longer claim this mechanism explains what Rick saw.** The fail-apart defect below is real and worth
fixing on the invariant's own terms — but **B1b, the log line, is now the primary deliverable rather than a
nice-to-have.** It is the instrument that tells us what actually happened, and without it the next attempt is
another guess.

⚠️ This is the second time today I attached a true observation to the wrong mechanism — the first was blaming
the poll timer for a hang that was `bloc.close()`. The observation here (a real invariant violation) survives;
the causal claim does not.

### 🔴 A SEPARATE FINDING, María's, in shared code — F1

`pane_polling_mixin.dart:95` states an optimisation the code below it **does not implement**:

> *`inactive` is treated as a stop WITHOUT a resume-refresh, so a shade pull costs one paused timer rather than
> a fresh request on the way back.*

The code cannot distinguish `inactive` from `paused`/`hidden`/`detached` — **all** of them set
`_appForeground = false`, so **any** of them followed by `resumed` yields `refreshNow: true`, i.e. exactly the
"fresh request on the way back" the comment says is avoided. Either the optimisation was lost in a refactor or
it was never written.

⚠️ **This mixin is used by three panes**, so it is a shared-code change with a blast radius, and the documented
behaviour and the real behaviour disagree — which is how the next reader inherits my mistake. **Filed, not
fixed. Needs its own row.**

### 🔴 REVISED after María's review — she named this better than I did, and her fix is smaller

My framing was *"a poll that returns without changing state"*, and I proposed a new retryable terminal state
for it. **That was more machinery than the defect needs, and it missed the sharper point**: this code already
states the rule it is breaking, six lines above the bug (`fleet_status_bloc.dart:140`):

> *⚠️ A FAILED CAP READ MUST NOT BLANK THE TABLE. The dial is one control; the table is the pane. They are
> fetched together but they **fail apart**.*

The cancel path violates that invariant **while holding a successfully-fetched composite in hand**. So this is
not an abstract "no state change" problem needing a new state — it is the one failure mode the author wrote a
comment to prevent, escaping through a door the comment did not cover. **No new state and no new builder
branch are required.**

**Work (revised — and María set the order, which is not the order I would have picked)**:

| Step | Item | Why in this position |
|---|---|---|
| **1st** | **B1b** — one debug line on the cancel path (`if ( debug ) print(...)`, house style) | 🔴 **It goes FIRST, on María's call.** It is the only item that can tell us whether Rick's spinner is the defect we found or a different one still unidentified. Building the fix first risks declaring victory over a bug that was never his. |
| 2nd | **B1a** — the dial fails apart from the table **including on cancel**: emit `FleetStatusLoaded( composite )` with a null-or-last-known cap whatever happens to `fetchSizeCap` | Satisfies the file's own stated invariant. Right on its own merits whether or not it is Rick's bug. |
| 3rd | **B1a′** — the **no-data** cancel keeps returning | ⚠️ **Both fixes get built, not one.** The outer `on DioException … if cancel: return` serves two callers: a cancel of `fetchState` has **no composite**, and returning is correct there — the pane really is going away with nothing to show. So the data-in-hand handling belongs **inside the dial's own try**, beside the existing `on FleetApiException`. Fix it in the outer catch instead and a cancelled composite fetch starts emitting an empty table. |
| 4th | **B1c** — two tests, not one | A cancel of **the dial** leaves the table rendered; a cancel of **the composite fetch** still adds nothing. The second is what stops B1a′ regressing into the first. |
| 5th | **B1d** — re-walk item 8 on device | With B1b in place, a persisting spinner names its own cause instead of costing another evening. |

**Size**: all small and self-contained. **Highest priority of everything here** — it is the one item where a
whole accordion is unusable.

  broadcast endpoint currently sends a message with no recipient list, so **the server may not accept one.**

### M1 — the headline, and the rule is conditional

`notifications.js:11189-11207`. **Not** a fixed three-part string:

| Condition | Renders |
|---|---|
| `parked > 0` | `Live: L · Parked: P · Total: L+P` |
| `parked <= 0` | **`Live: L`** — not `L`, and **not** `Live: L · Parked: 0 · Total: L` |

The reasoning is in the source and worth keeping: *"LIVE" is unconditional; the parked split is not.* The label
always rides along because the number sits beside a second number (a closed-vs-new ratio), and *"a bare integer
next to a bare decimal is two unlabelled quantities the reader must tell apart by shape."* The parked split **is
a disclosure — it earns its space only when there is something to disclose.**

⚠️ And parked rows are excluded from "live" deliberately: *"Parked rows are approved-not-now, blocked on
nothing, and self-expiring; counting them alongside live work makes the remaining-work figure fiction."*

### M2 — it is the `⋯` disclosure, and it carries the controls

`multiplexer/render/templates/rowDisclosure.ts`, quoting **his own spec** from the JS source:

> *"an ellipsis right-justified ON THE TITLE LINE indicating hidden functionality; clicking it discloses the
> controls as ONE narrow row spanning the full width of the item; that second row is NOT displayed by default."*

So it is **both** of the readings I was going to ask him to choose between: a disclosure whose disclosed row
holds the edit controls. Glyph `⋯` (U+22EF), title *"Show row controls"*. Behind it: `Blocked by · Next chase ·
Accountable · Filed by · Project` plus nine controls.

🔴 **The state lives in `aria-expanded`, NOT in a CSS class** — and the `hidden` attribute carries the visual
half. **Both are required.** The source is explicit about why a port that keeps one *"looks correct to a sighted
mouse user while being unreachable by keyboard, or reachable but never painted."*

### M3 — 🔴 not a filter. A lookup by hash, and both my options were wrong

`multiplexer/render/taskLookupBox.ts`. I framed this as client-side filter vs server-side search. **Neither.**
It is a box you paste a task hash into, which returns **that ticket**.

His words, quoted in that file: *"Every time someone refers to a row for a ticket by # I have no idea what
they're talking about."*

Three constraints the source pins, none of which I would have guessed:
1. 🔴 **It must hit `/api/tasks/<ref>`, never `/api/tasks?id_prefix=<ref>`.** The query form chains an owed
   filter after the prefix match and therefore **hides holding-area rows — measured, exactly 1 of 23 held rows
   was findable that way.** The single-row endpoint applies no visibility filter.
2. **A result card, not scroll-to-row.** The hashes he is handed are usually for rows **not on his board** —
   held, parked or terminal — so reveal-and-highlight would only work for the set that never needed a lookup.
3. **The status is part of the answer, not decoration.** A held row rendered without its status reads as an
   ordinary queued ticket, *"and the difference between 'it is queued' and 'it is sitting in your holding area'
   is usually the whole reason he is asking."*

⇒ The URL is built by `shared/task-lookup.js`, whose own tests pin it. **Do not inline the path.**

## 5. 🔴 Holding Area: NOT a bug — needs his ruling, R1

**His report**: *"a weird grouping bug that lists Tiffany twice, that lists multiple Mr Radios each one with
different tasks listed under them. So that's a little bit buggy."*

**It is working as designed, and the design has a reason I do not want to overturn on my own.**

`groupByFiler` (`holding_area_models.dart:48`) keys on the **whole `created_by` string, session hash
included** — `"mr radio 078b97cb"`, not `"mr radio"`. So one persona across three sessions is three groups.
The file states why, and it is a safety argument rather than a preference:

> *Stripping the hash to group by bare persona would merge one persona's sessions into a single group — fewer,
> larger groups, and an approve-all whose blast radius is WIDER than the name on the button suggests… If the
> fleet wants per-persona grouping it is a ruling, not a tidy-up, because it changes what one press does.*

⇒ **The duplicate names are real sessions, not duplicate rendering.** What he is seeing is true.

**Three options, and this is his call:**

| Option | What it does | Cost |
|---|---|---|
| **A — leave it, label it** | Show the session hash more clearly in the group header, so three "Mr Radio" groups read as three *sessions* rather than a rendering fault | Smallest. Fixes the confusion without touching what approve-all does. |
| **B — group by persona, batch by persona** | One group per persona; approve-all acts on **every session's** rows | What he asked for, and it **widens approve-all's blast radius**. That is the thing the current design refuses to do silently. |
| **C — group by persona, nest sessions inside** | Persona is the outer group; sessions are the inner ones; batch controls stay at **session** level | Most work. Gets the readable list AND keeps blast radius honest. Pairs naturally with N2 below. |

⇒ 🔴 **RULED: B. Rick, 2026-09-22, in his own words** — *"I want you to group all sessions without any explicit
labeling under each persona. Collapse it. I don't give a shit about your notion of session, it's irrelevant to
me."* He also rejected the framing outright: *"I don't give a fuck if you did that on purpose or not. It's a bug
because it does not mirror the behavior or the layout of the multiplexer or the legacy notification client.
Don't try to defend a bad idea. It gets me the end user nothing."*

**He is right about the thing that matters most here**: mirroring the surfaces he actually uses is the
requirement, and I argued an internal safety property at him instead of answering it. My recommendation of C
is withdrawn — C was a compromise that kept a distinction he has now told me is worthless to him, and a
compromise nobody asked for is just a smaller version of ignoring the request.

### What B means concretely

- **One group per persona.** Sessions are merged and **not labelled at all** — no hash, no session count, no
  "3 sessions" subtitle. The session is not a user-facing concept on this surface.
- **Collapsed by default**, which is N2 below — so B and N2 are now **one piece of work**, not two.
- Groups ordered by persona name, case-insensitively, as today.
- The trailing **Unattributed** group stays: a row with no filer must still be visible somewhere.

### One thing B still requires, and it is inside B rather than an objection to it

Approve-all on a persona group now acts on **every row that persona filed across all their sessions**. That is
the intended behaviour. So the **count on the button and in the confirm must be that number** — the wider
number — and not a per-session subset. That is not the old design reasserting itself; it is what makes B
correct. A batch control whose label undercounts what it does is a defect under any grouping scheme.

⇒ Builds as: `groupByFiler` keys on the persona portion of `created_by`; the group's `ids` (the blast radius as
a value) then naturally covers every session, and the existing label/confirm machinery reports it.
