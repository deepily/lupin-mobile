#### 🔴 F-Clayton-S2-D — `canRecord` clause (d) is a MISSING GUARD, not a clause needing invention

## §5 Post-cascade fold bundle

### OSQ3 — RULED 2026-08-30. Implement as specified below.

**Not to be confused with the stop-list collision.** Two different questions, checked against each other before the final ask. The **stop-list** question — a stop-list pattern matching an incoming answer or question and suppressing it — was raised by Sam, **decided inside the group** (see §4), and was never owed to the user. **OSQ3 was about the pause boundary.**

**The collision it resolved.** Ruling 2 said a tap pauses playback. Ruling 4 removed the fraction cut so answers speak in full. Together, pause had nothing to land on: `pause()` sets a flag and the in-flight utterance finishes naturally, so with the whole answer as one utterance a tap could not take effect until the answer had finished — inert on exactly the long answers it was added for. `StreamingTtsPlayer` exposes no mid-utterance position (OSQ-5), so utterance-level granularity is the only implementable kind.

#### THE RULING (Rick, 2026-08-30)

**Sentence-sized chunks, WITH synthesis running ahead of playback and cached locally.**

> *"Let's go with sentence size chunks per your recommendation. But what I want to do is allow the text-to-speech generation to run at full velocity and get cached locally for replay. That way there would be no gap after the first sentence — because while the first sentence is being played as audio, the second and third and successive chunks will also be translated into audio."*

**This is more than the option that was offered.** The recommendation was chunking alone, which trades a small inter-sentence gap for a working pause. Rick's addition removes that trade: **decouple synthesis from playback.** Four requirements fall out, and **none is in the input plan today**:

1. **Synthesis runs ahead at full velocity**, not lock-step with playback. Chunk *N+1* is already audio before chunk *N* finishes speaking, so the seam between sentences is **inaudible**.
2. **Chunks are cached locally as audio.** The cache is what makes replay cheap and what makes the run-ahead worth doing.
3. **Replay serves from that local cache, not from re-synthesis.** This settles a question the plan never asked: replay-from-start becomes a cache read, so it is fast and cannot drift from what the user originally heard.
4. **Pause lands at a chunk boundary** — the granularity the player can actually honor. Both original rulings survive: nothing is cut (ruling 4), and a tap stops at the end of the current sentence with the rest queued (ruling 2).

#### The four requirements, reified as acceptance criteria

**The Steward's gate finding**: §5 said these four were "in no AC today" and then named none of them to one — so **nothing could go red if an implementer shipped chunking without the run-ahead**, which is the exact failure this section warns about. This document tells the implementer to ask what would have to break for each AC's test to go red; these had no test to go red. Reified:

| AC | Requirement | Falsified by |
|---|---|---|
| **AC-S3.10a** | Synthesis runs AHEAD of playback: chunk *N+1* is audio before chunk *N* finishes | An implementation that synthesises chunk *N+1* only after *N* completes — assert the inter-chunk gap is below an audible threshold on a ≥3-sentence answer, under `fakeAsync` with a stubbed synthesiser recording call order |
| **AC-S3.10b** | Chunks are cached locally as audio, keyed per chunk | An implementation holding only the current chunk — assert the cache holds *N* entries after an *N*-sentence answer completes |
| **AC-S3.10c** | Replay serves FROM the cache, never re-synthesis | An implementation calling the synthesiser again on replay — assert zero synthesiser invocations during a replay of an already-played answer |
| **AC-S3.10d** | Pause lands at a chunk boundary, and the remainder stays queued | An implementation that cuts mid-chunk, or that drops the remainder — assert playback stops at the end of the current sentence AND the remaining chunks are still queued on resume |

⚠️ **AC-S3.10a is the load-bearing one.** Chunking without the run-ahead technically satisfies the ruling's first word and ships the exact gap the ruling exists to remove. Without this AC, that implementation passes.

**Interaction the implementer must not miss**: requirement 3 sits directly on top of row `a3fdb6ad` (`pausedStream` has no replay on subscribe) and on AC-S3.4b's *replay implies resume*, which per AC-S3.9 drains the whole backlog globally. **A cached replay does not change the global-drain decision** — ratified separately in §4, and it stands.
