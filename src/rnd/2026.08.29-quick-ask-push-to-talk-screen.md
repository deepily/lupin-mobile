# Quick Ask — push-to-talk Q&A screen (round 1)

## Context

Rick wants the simplest useful version of the notification client's Q&A card, on the phone: hold a
big pulsing button, speak a question, release, and get an answer back — with an honest status
indicator in between. The questions are **short-lived agentic runs**, not the long-running deep
research / podcast / SWE jobs.

This is deliberately **round 1 of two**. Round 2 (a later session) becomes a multi-job window that
tracks concurrent requests as CJ-Flow-shaped cards across **todo / running / done / dead**, mirroring
the notifications-client accordion. Round 1 is one live question at a time — but every data shape
here is chosen so round 2 is a rendering exercise, not a rewrite.

**Round 1 has two halves.** The Quick Ask screen itself (§1–§6), and — per Rick's ruling 5 — the
start of the **generic channel for the server asking the phone a question** (§6a), because that
channel can block the server outright and is the strategically important half.

### What already exists (reuse, don't rebuild)

| Need | Already built |
|---|---|
| Push-to-talk capture | `lib/services/asr/asr_service.dart` — `startRecording()` / `stopAndTranscribe()` / `cancelRecording()`, WAV 44.1k mono → `/api/upload-and-transcribe-wav` → transcript. Mic permission handled, with a `requestMicPermission` test seam on `voice_reply_field.dart` |
| Asking | `QueueRepository.ask()` → `POST /api/v2/ask` |
| Speech + pause/resume/replay | `lib/services/tts/tts_orchestrator.dart` — `pause()` holds at an utterance boundary (nothing dropped), `resume()`, and an `urgent` enqueue already preempts and **replays the interrupted utterance from the start** |
| WS transport | `lib/services/websocket/websocket_service.dart`; mobile subscribes with `subscribed_events: []`, which the server reads as `["*"]` — **all frames already arrive** |

### The gap this plan closes

The server emits **`job_state_transition`** per job — `pending→queued` (`todo_fifo_queue.py:1400`),
`queued→running` (`queue_consumer.py:198`), `running→completed` (`running_fifo_queue.py:636,741`) —
and the **completed frame carries the answer** in `metadata.response_text`. Status and answer ride
the same wire.

**Mobile drops every one of these frames**: `WsBlocDispatcher` (`lib/app.dart:43`) has no case for
`job_state_transition`. It handles `queue_todo_update` / `queue_running_update` / `queue_done_update`
/ `queue_dead_update` instead — and those four names have **zero emit sites in the server** and are
absent from `websocket available events` in the INI. Nothing has ever emitted them; the parent repo
already measured this and wrote the receipt into `src/tests/lupin_smoke/test_queue_workflow.py:280`.

⇒ Mobile's job-status wiring is dead today. `QueueDashboardScreen` has never live-updated. Wiring
`job_state_transition` is both what Quick Ask needs and the repair for that.

## Findings that shape the design (all verified in-tree)

**1. The status frame beats the HTTP response — always, not sometimes.**
`v2/executor.py:198-201` calls `self.todo_queue.push( job )` — which emits `pending→queued`
*synchronously inside `push()`* — and only then `return Outcome( status="waiting", job_id=... )`.
The frame is on the wire before FastAPI serializes the body. On a cache hit the consumer can also
emit `queued→running` and `running→completed` in that same window. **A client that starts listening
after it learns the job id will routinely miss frames, and can miss the entire job.** ⇒ buffer
unattributable frames.

**2. There is no terminal event for a server restart.** `JobState.INTERRUPTED` appears only in a DB
startup sweep (`job_persistence.py:683,728`), never in a WS emit. A bounce mid-job produces *no*
frame — the UI spins forever. ⇒ a silence watchdog is required, not optional.

**3. `GET /api/job-history/{job_id}` is the wrong reconcile door — it will 404.** All PostgreSQL
persistence is gated on `is_agentic_job_type()` (`queue_util.py:91`) against a 10-entry allowlist
(`job_persistence.py:77`). A plain question is not an agentic type, so no row is written. The
working door is **`QueueRepository.getQueue('done'|'dead'|'run'|'todo')`** — `routers/queues.py:391`
puts `response_text` into the done-queue metadata and `JobSummary` already parses it.

**4. Two gates silently swallow the answer.** The queue speaks as `queue.done@lupin.deepily.ai` with
no persona, so `TtsSender.isPersona` is false and `_systemSenderMuted` drops it when
`speakSystemSenders` is off; and `_formatSpeech` cuts every message to `prefs.ttsFraction` —
**Rick set that to 20% on 08-21**. Both were built for previewing chatter the user did not ask for.
⇒ see Rick's ruling, §Decisions.

**5. `AskResponse` has no `waiting` branch — a live bug.** `queue_models.dart:219-221`: `isDone` /
`needsInput` / `isFailed` are all false for `status:'waiting'`, so `summary` falls through to
`'Done ($path)'`. `submit_job_sheet.dart` pops its sheet and reports success for work that has not
started. `pushAgentic()` already knows about `'waiting'`; the knowledge never reached the model.

**6. `WebSocketService.sessionId` is not stable** — refetched on every `_establishConnection()`,
so it is null before connect and changes across reconnects. Harmless for correlation (transitions
are user-scoped) but it cannot be a correlation key.

**7. The completed metadata is already card-shaped.** `running_fifo_queue.py:1692-1710` carries
`question_text, agent_type, status, is_cache_hit, started_at, completed_at, duration_seconds`
(+ `abstract`/`report_link`/`cost_summary` on agentic paths), tagged in-source *"Phase 6.2:
Card-rendering fields for client-side card creation."* It is field-compatible with `JobSummary`.
**Parse all of it in round 1 and round 2's card view is mostly built.**

## Decisions (Rick's rulings)

| # | Ruling |
|---|---|
| 1 | **Send immediately on release** — no confirm step. Transcript still renders as the question bubble. |
| 2 | **Auto-speak**, with **tap-to-pause** (resume later) and **replay from the beginning**. |
| 3 | **Scrollback kept**, **record button pinned at top**, **newest Q&A pair on top**. |
| 4 | **Answers always full, always audible** — override both the preview-fraction slider and the mute-system-senders switch. *"We are requesting an ask-and-answer pair, audio in audio out… what we really want is to pause and/or rewind an answer we've already captured."* Those two settings keep governing everything else. |
| 5 | **Start the generic "server asks the phone a question" surface now** — overriding my recommended shortcut. *"I'm more interested in allowing the server to respond with whatever it needs to satisfy a given query… how can the server talk to us on the cell phone when it needs information from us — that is a strategically important piece of behavior."* Noting it can be a **synchronous blocking call: all processing halts on the server until the phone answers.** |

### 1. Shared lifecycle vocabulary — `lib/features/queue/domain/job_lifecycle.dart` (NEW)

Mirror the server's own map (`src/cosa/rest/job_state.py:74`) rather than inventing one. Note
**`stalled → todo`, not dead** — a stalled job is resumable; a hand-rolled map gets this wrong.

```dart
enum JobLane { todo, run, done, dead }

enum JobLifecycleState {
  pending, queued, scheduled, paused, running,
  completed, failed, interrupted, cancelled, stalled;

  static JobLifecycleState? parse( String? raw );  // null on unknown ⇒ drop the frame
  JobLane get lane;                                // verbatim STATE_TO_UI_CONTAINER
  int     get rank;                                // monotonic guard, see §3
  bool    get isTerminal;                          // completed|failed|cancelled|interrupted
}
```

Quick Ask's three displayed forms are a **pure projection** of `lane` — no fourth concept is
introduced, so round 2's grouping is `groupBy( entries, (e) => e.state.lane )` with zero rework.
It lives in the *existing* queue feature's domain layer so both screens import it without either
depending on the other.

### 2. Card model — `lib/features/quick_ask/data/quick_ask_models.dart` (NEW)

`QuickAskEntry` carrying the **full** finding-7 metadata, with two constructors —
`fromTransition( Map data )` and `fromSummary( JobSummary s )` — so a frame and a reconcile fetch
produce the same shape.

### 3. `QuickAskBloc` — `lib/features/quick_ask/domain/` (NEW)

A dedicated bloc, **not** an extension of `QueueBloc`: `QueueBloc`'s state is a single-slot
discriminated union whose members clobber each other, and `_onExternalUpdate` early-returns unless
the dashboard is loaded — an in-flight ask would be wiped by any dashboard refresh.

Correlation is a **rank-monotonic reducer with a pre-attribution buffer and a silence watchdog**:

- **Buffer** — before the job id is known, frames land in a bounded ring (32 entries / 60s TTL).
  On the `AskResponse`, drain filtered by `jobId` and fold in rank order. *Answers finding 1.*
- **Monotonic fold** — apply a frame only if `rank(to) > rank(current)`, except terminals which
  always apply. Duplicates and reorders become no-ops; a missed `running` is repaired by `completed`
  landing directly.
- **Watchdog** — one timer, reset on every accepted frame; fires after 45s of silence.
- **Reconcile** — `getQueue('done')` → `('dead')` → `('run')`/`('todo')` scanning for the job id.
  Found in done → complete with `responseText`; in dead → failed with `error`; still alive → rearm
  (45s, 90s, 180s); absent after 3 probes → a `lost` state with a Retry affordance.
  **Never `getJobHistoryEntry` — finding 3.** *Answers finding 2.*
- **Belt channel** — a `notification_queue_update` whose `notification.jobId` matches the live job is
  independent completion evidence (its `message` *is* the answer). One extra dispatcher line.

Also fix finding 5 while here: give `AskResponse` an `isWaiting` branch and stop `summary` reporting
`'Done'` for queued work.

### 4. Screen — `lib/features/quick_ask/presentation/quick_ask_screen.dart` (NEW)

Record button **pinned as a fixed header** (not list item 0, so the list can become the grouped card
view untouched), newest-first `ListView` below. Long-press to record with a pulsing animation,
release to submit. Status chip per card driven by `JobLane`. Pause toggle renders from
`TtsOrchestrator.pausedStream` — **never a local bool**, or this screen and `FocusModeScreen`'s
existing pause toggle will disagree. Replay button on any done card with a non-empty answer.

Registered as a `ListTile` in `_legacyDrawer` (`focus_mode_screen.dart:178`) — the app has no route
table; navigation is imperative pushes.

### 6. Speech ownership

`FocusChatBloc` stays the **sole dispatcher of inbound WS frames to speech** (AC-S2.8, pinned by
`test/service_integration/focus_app_wiring_test.dart:83`). Quick Ask does **not** enqueue on a
`completed` frame — the queue already speaks the answer unconditionally, so doing so would double-speak.

Quick Ask drives the orchestrator for **user gestures only**: `pause()` / `resume()`, and replay via
an `urgent` `enqueueAlways` with a named `TtsSender` — urgent preempts and replays from the start
(the existing mechanism, matching ruling 2), and a non-empty `name` makes `isPersona` true so replay
works even when system senders are muted. Amend AC-S2.8's wording from "sole caller" to "sole
frame-driven dispatcher", and add a test that a frame arriving while Quick Ask is mounted still
produces exactly one enqueue.

**Ruling 4 — answers speak in full, always.** Add an optional `verbatim` flag to the orchestrator's
enqueue that skips `_formatSpeech`'s fraction cut and the `_systemSenderMuted` gate. `FocusChatBloc`
sets it when the inbound notification's `job_id` matches a live Quick Ask job — `QuickAskBloc`
exposes a small read-only `isQuickAskJob( id )`, which keeps the enqueue in one place while letting
the answer be recognized. Default stays off, so nothing else changes behavior.

### 6a. The question channel (ruling 5) — branch on STATUS, not on which id is present

> **María's ruling (thread `a14d9b29`, 2026-08-29) corrected this section twice.** My first draft
> picked the submit door by which id was present. That is wrong: there is a **third case with no id
> at all**, and a **fourth door that blocks the HTTP call**. Both are below.

**There are two different ways the server asks the phone something, and they are not the same door.**

| | **A — "I need an argument"** | **B — "I need a decision"** |
|---|---|---|
| Trigger | `/api/v2/ask` can't extract a required arg | `notify()` / `ask_yes_no` / `ask_multiple_choice` / `converse` |
| Arrives as | the **HTTP body**: `status:'parked'` + `pending_id`, `answer` = the question | a **WS `notification_queue_update`** whose `notification.response_requested == true` |
| Answered via | `POST /api/v2/resume` `{pending_id, answer}` | `POST /api/notify/response` `{notification_id, response_value}` |
| Is the server blocked? | No — the pending entry just waits | **Yes.** `notifications.py:1401` holds an SSE stream on `asyncio.wait_for( event, timeout_seconds )` until the phone answers or the timeout substitutes `response_default` |
| Mobile today | ❌ no repo method at all | ⚠️ partly built — see below |

Verified: `flow.py:1255` `_speak()` sends a plain notification with **no `response_requested`**, so a parked question is *spoken* but carries no answer affordance. Channel A really is HTTP-only.

#### Door C — the near-match confirmation, which BLOCKS the ask (María, verified)

`_near_match_replay` / `_user_confirms` (`flow.py:854, 928`): when a question scores close to a
cached one but below exact, the flow asks the user *"Is that the same as: …?"* — a **yes/no
`response_requested` notification** — and **blocks the HTTP request thread waiting for the reply**:
`timeout_seconds = 30`, `retry_on_timeout=True, max_attempts=3, backoff_multiplier=2.0` ⇒ 30s at
minimum, ~210s worst case. The prompt defaults to **"no"** (a wrong replay is worse than a re-run),
and a confirmer that raises counts as a no.

🔴 **This is live on the dev server Rick uses.** `similarity confirmation enabled = true` sits in
`[Lupin: Development]` (`lupin-app.ini:497`); it is `false` only under `[Lupin: Testing]` (`:637`).

🔴 **And mobile's shared Dio gives up at 30 seconds** (`http_service.dart:45`,
`receiveTimeout = 30s`) — the same instant the *first* confirm attempt expires. So today the ask
would time out on the phone while the server is still retrying, and the confirm would always
default to "no" with the user never seeing the question.

**Two consequences the plan must carry:**
1. The Quick Ask ask-call needs its **own longer `receiveTimeout`** (per-request `Options`, not a
   global change — 30s is right for every other call).
2. The question surface must be able to **answer a WebSocket question while the phone's own ask
   call is still in flight**. That is not a nicety: without it the cache-replay path can never be
   confirmed. It is also the strongest possible argument for Rick's ruling 5.

#### The five outcomes to branch on — `status` first, then the id

María: *"Branch on `status` first — parked vs needs_input vs response_requested — and treat
`needs_input` as 'server is telling you, not asking you.' Then use the id to pick the endpoint."*

| `status` | Meaning | Client action |
|---|---|---|
| `done` (+ `answer`) | replay served from cache, or inline executor | render + speak |
| `waiting` (+ `job_id`) | queued; answer comes over WS | the §3 correlation machinery |
| `parked` (+ `pending_id`) | Door A — needs an argument | prompt widget → `POST /api/v2/resume` |
| `needs_input` (**no id**) | **the third case.** `flow.py:365` hard-codes `interactive=False` on the `submit` path, so it never parks — this is the server *telling*, not *asking* | terminal card naming `args_missing`. **No answer affordance** — there is nothing to answer to |
| `rejected` / `failed` | refused or errored | error card |

Plus, orthogonally at any time: a **`response_requested` notification** (Door B, and Door C's
confirm is one of these) arriving over the WebSocket.

**Rick's ruling is channel B**, and it is the one that blocks. The good news is that mobile already has most of B:
`POST /api/notify/response` is already wired (`notification_repository.dart:42`), and yes/no (with Neither + `[comment: …]`), open-ended, and single-select multiple-choice already render inline in `focus_chat_pane.dart` via the shared `prompt_bodies.dart`. **The surface exists; what's missing is the lifecycle** — precisely the blocking part Rick named.

**Round 1 scope for the question channel** — make the existing surface honest, then hang channel A on it:

1. **Lifecycle (the strategic gap).** `notification_expired` and `notification_responded` appear **zero times in `lib/`** — the frames arrive and are dropped. Add both dispatcher cases: expired → mark the ask dead and show "⏰ Expired — default used: X"; responded → another device/proxy answered, retire the card. Fold `state == 'expired'` into `FocusMessage.answered` (today an expired ask stays "pending" forever and poisons `pendingPromptFor`, so the composer tries to answer a dead ask and takes a 400 the user never sees). Add a countdown from `timeout_seconds` (parsed, never read) and use `response_default` (parsed, never read) for prefill and for a cancel-with-default. Branch the 400 on `"already responded"` / `"grace period exceeded"` instead of collapsing to a generic error.
2. **Fix the multi-question payload defect.** Mobile reads `response_options['options']` at the top level; the real wire nests `response_options.questions[]`, each with its own `question / header / multi_select / options`. So **a canonical `ask_multiple_choice` payload renders an empty option list on the phone today**, and the submitted value is a bare label rather than the `{"answers": {header: value}}` JSON the server parser expects. First cut: a simple one-question-at-a-time stepper, no Back/Next wizard.
3. **Hang Door A on the same widget.** Add `QueueRepository.resume( pendingId, answer )` → `POST /api/v2/resume`, and render a `parked` response using the *same* prompt body as a `response_requested` notification. One question UI; the **submit door is chosen after branching on `status`** per the table above, never by sniffing for an id. `needs_input` gets a terminal card with no answer box. This is what makes the widget generic rather than notification-specific — and it means "which city?" gets answered by voice in place, which is what Rick asked for.
4. **Survive Door C.** Give the ask-call its own `receiveTimeout` (≥ 240s, covering the ~210s worst-case confirm ladder) via per-request `Options` — never by loosening the global 30s, which is right for every other call. Keep the record button disabled but **the question surface live while an ask is in flight**, so the phone can answer the near-match confirm that its own ask is blocked on. Add a visible "waiting on your confirmation" state so a 30-second silence is explained rather than mysterious.

```
S1 ──▶ S2        S1 provides the lane vocabulary S2's status chips render
S3 ──▶ S2        S3 provides the replay/pause controls S2 mounts
S4 ──▶ S2        S4 provides the prompt widget S2 shows inside the Quick Ask pane
```

**Provides / consumes, stated both directions:**
- **S1 provides** `JobLifecycleState` / `JobLane` and the live-job state stream. **S2 consumes** them
  for the three status forms. S1 needs nothing from S2.
- **S3 provides** the `verbatim` enqueue flag and the pause/replay controls. **S2 consumes** them as
  buttons. S3 needs nothing from S2.
- **S4 provides** the prompt widget and its submit-door routing. **S2 consumes** it for the parked /
  confirm cases. S4 needs nothing from S2 — it also serves the existing focus surface.
- **S1 ↔ S4** are independent: S1 handles `job_state_transition`; S4 handles
  `notification_queue_update` questions and HTTP statuses. They meet only at S2.

**Open decision the cascade must resolve:** §6a.4 — the `interactive=false` vs long-timeout trade
(it changes S4's scope materially, and would partly reverse Rick's ruling 5).

**Scope note for reviewers:** S4 repairs an existing shared surface used by focus mode today, so its
